01 / VISION & PLATFORM

平台目标与核心决策

建设 NBDB 结构生物学统一分析与计算平台：让研究者在同一平台中发现数据、选择现有科学软件、准备运行环境、提交计算、进行交互分析，并管理全部成果。AI 搜索演进为平台的自然语言入口和 Agent 编排层。

平台目标：结构生物学的各种分析都能在 NBDB 中完成覆盖结构数据分析、实验原始数据处理、结构解析与精修、预测建模、对接、模拟、自由能、核酸及整合建模等方向。通过标准工具接入协议持续扩展，工具中心、Agent、工作流和交互计算共用项目、数据、任务、权限和计算资源。

现成软件已经实现了大量专业算法，平台建设重点是把这些能力真正组织成可运行的服务。每种软件配置独立环境、明确输入输出、资源与许可条件，再由 Agent 发现和调用。单个工具、完整软件套件、已有实验室服务和用户研究代码都应有接入路径。

统一能力入口

工具中心与分析应用

按分析目的、数据类型、分子类型、资源和接入状态检索工具；用户可以直接指定方法运行，无需先存在预置配方。

统一科研执行

计算、工作流与交互会话

短任务、长作业、GPU/MPI、多步骤工作流、Notebook 和图形应用均进入统一运行账本，计算过程与成果留在项目中。

智能组织能力

Agent 发现、规划与解释

根据问题与数据查找当前可用工具，准备参数和环境，安排依赖、检查结果，并将专业软件输出汇总为可核对的研究成果。

平台承诺与交付方式

  1. 总体范围覆盖完整分析生态。分期安排工具接入和自动化深度，首批演示不定义平台最终边界。
  2. 接入后能够实际执行。工具卡片必须关联可用运行端、环境、输入契约和产物；只列软件名称或跳转官网不算完成接入。
  3. 单工具、用户工作流与 Agent 共用底座。同一个操作可由表单、API、Notebook 或自然语言触发，生成一致的 RunSpec。
  4. 专业软件承担计算。Agent 理解与编排，算法由经过配置的科学软件执行；平台复用和集成成熟生态。
  5. 人工参与也纳入平台。建模、谱峰指认、粒子选择或参数判断等步骤可进入交互会话，完成后保存结果并继续工作流。
  6. 新增工具不重写平台主干。通过软件包、操作、部署和验证描述注册，自动生成表单、API 和 Agent 工具说明。

“各种分析都能执行”是平台的承载与扩展目标；每个具体操作是否可用，仍取决于它的部署状态、输入、授权和资源。平台应显示这些条件并提供接入或资源配置路径，避免把尚未安装的软件呈现为已可运行。

平台成功指标经过真实数据验证的分析领域覆盖度、可运行操作覆盖度、跨工具工作流完成率、研究者在平台内完成任务的比例，以及结果复现与科学可接受率。工具数量只是其中一个维度。
02 / AGENT CORE ARCHITECTURE

Agent 核心架构图

Agent 的核心是一个有状态、受约束的执行循环：模型提出计划，程序校验和执行工具，真实结果形成 Observation，再决定继续、请求人工判断或交付成果。

模型负责什么

理解问题、选择可用操作、组织步骤、根据 Observation 调整计划，并解释有证据的结果。Planner 和 Reporter 是逻辑角色，可共享模型服务。

程序负责什么

类型、身份、预算、版本、任务状态、作业提交、结果解析与领域检查由代码控制。持久化状态保存计划、尝试、产物和证据，避免把对话历史当计算状态。

接入成熟度与实时可用性分别显示

成熟度意味着什么产品行为
M0 · 已登记已有用途、文档和接入方案可以浏览，不能宣称可以执行
M1 · 已部署 / 已连接环境或远程服务已配置，依赖与许可已登记展示部署条件与缺失项
M2 · 可执行功能探针和最小真实任务通过可以按权限手动运行；明确尚未验证的范围
M3 · 已验证指定操作、环境和输入范围通过科学与工程验证可进入对应范围的可信 Agent 工作流
M4 · 工作流验证跨操作流程、异常处理和结果解释经过领域验收可以作为推荐流程；继续标明人工节点和适用条件

另设实时状态：可用、资源排队、缺许可、缺数据库/权重、服务离线、维护中、权限不足。规划时和提交时都检查部署；同一软件可在不同站点、版本或操作上处于不同状态。

新增软件的标准接入流程

  1. 登记软件及用途，确认来源、维护者、许可和实际接口。
  2. 构建固定环境或连接现有服务，登记数据依赖和资源需求。
  3. 为具体操作编写 manifest、参数构造器、产物收集器与功能探针。
  4. 使用真实最小样本完成试运行，验证文件与元数据完整性，开放 M2 手动运行。
  5. 增加领域基准、边界样本、错误处理和解释模板，通过后提升相应操作验证等级。
  6. 自动生成表单和 API，纳入 Agent 检索；软件升级产生新版本并执行回归。
能力扩展的关键验收工程团队接入一个此前不存在的软件时，只增加连接器、环境和契约，不修改平台任务引擎和前端业务页面。若新工具确需全新交互组件，可以扩展查看器/表单插件，其他执行机制继续复用。

07 / EXECUTION & SESSIONS

通用执行与交互计算

为工具的不同运行方式提供统一适配协议。商业或学术许可是横跨各种协议的运行条件，具体软件仍通过命令行、库、服务或图形会话执行。

接入方式平台如何执行必须登记的能力差异
CLI / 批处理程序在固定环境运行允许的程序与结构化参数，隔离工作目录，解析/收集输出线程/MPI/GPU、退出码、超时、检查点、交互提示、正式输出格式
Python / R / 其他库使用固定环境调用注册函数，或者在项目 Notebook 中运行研究代码依赖锁、函数/脚本版本、异常、对象序列化与内存需求
远程 API / 实验室软件服务连接器负责身份、提交、轮询/回调、限流、取消和产物导入外发范围、费用、保留期、取消支持、远端状态与许可
已有工作流引擎提交版本化工作流和参数，记录引擎 Run ID、子任务及环境由谁负责子作业调度、恢复、缓存和重试；避免双重管理
图形应用 / 人工节点启动授权远程应用或桌面会话，挂载项目资产，保存用户输出后继续流程人工操作范围、会话时长、图形加速、可重放程度和输出核验
用户自定义工具 / 脚本在受控项目环境试运行，登记脚本、依赖和输入；需要复用时发布为注册操作网络/资源权限、可见范围、环境锁定、研究性验证状态

人工与自动任务在同一条流程中

自动预处理 → WAITING_FOR_USER → 平台内 Coot / CCPN / Notebook 会话
                                     ↓
                            保存产物并提交完成
                                     ↓
                            文件与科学前提校验
                                     ↓
                          自动精修 / 统计 / 报告

会话断线不等于作业终止；文件持久化也不保证 GUI 内存状态可恢复。平台保存应用、环境、输入、人工选择说明和产物；无法逐操作重放时，明确标记“人工参与记录”。用户不需要离开 NBDB 项目重新整理一套结果。

“都能在平台执行”的实际含义可托管工具在平台资源运行；需机构授权的软件可在已授权运行端执行；具有正式 API 的服务可集成提交与取回；需要人工判断的应用通过交互会话参与。只有官网网页且无允许的稳定接口时，先保留待接入状态，不能用不可靠网页自动化冒充已集成计算。
08 / SCIENTIFIC WORKFLOWS

跨领域端到端工作流

以下流程描述平台目标与接入方式，具体工具从当前部署目录解析。它们用于检验不同计算类型是否都能在同一平台贯通，接入状态不会因示例而自动变为“可运行”。

“把这套冷冻电镜数据导入 NBDB，完成处理、重构和模型验证。”
  1. 登记原始数据。导入 movies/微图或 tilt series、采集元数据和项目已有中间结果，核对存储与资源。
  2. 选择处理后端。从已就绪的 RELION、授权 CryoSPARC 或其他流程后端中选择；区分单颗粒和断层流程。
  3. 处理与人工检查。按流程进行运动校正、CTF、粒子/区域选择、分类和重构；需要判断时进入平台交互节点。
  4. 建模与精修。用适用预测/模板和建模软件得到初始模型，通过 Coot 等检查，再使用所选精修工具。
  5. 验证并交付。记录数据划分、处理、掩膜和坐标，交付地图、模型、验证指标、工程文件与谱系。
领域验收：不能凭有最终地图就声称完成独立 half-map 验证；所有处理软件必须有真实可用部署。
“处理衍射数据，尝试分子置换并精修结构。”
  1. 整理实验输入。登记衍射帧、实验几何、序列和模板，检查数据格式和伴随元数据。
  2. 处理衍射数据。按已接入的 DIALS/XDS 与 CCP4 等操作进行索引、积分、标度及质量分析。
  3. 定相与建模。按数据条件选择分子置换或实验定相路线，使用 Phaser/Phenix/CCP4 等实际可用操作。
  4. 交互修正与精修。将待检查区域送入 Coot 会话，保存模型后继续所选精修程序。
  5. 报告。保留反射数据、测试集标识、地图、模型、质量报告和失败策略。
领域验收：空间群、反射列、自由 R 测试集与模型假设由领域规则检查；解析成功与模型可靠分开评估。
“为这个体系建立模型，准备模拟并分析构象变化。”
  1. 明确体系。确定序列、链、化学组分、环境、实验约束和研究目标，选择可用预测/建模工具。
  2. 生成并检查模型。运行授权预测/建模环境，保存权重/数据库版本、模型集合与置信信息。
  3. 建立模拟体系。选择力场、配体/修饰参数、质子化、溶剂/膜和边界条件，核对拓扑与坐标。
  4. 执行模拟。按计划运行最小化、平衡、生产和必要重复，使用 GROMACS/OpenMM 等部署，保留检查点。
  5. 轨迹与统计。执行 PBC/拟合等显式处理，计算 RMSD/RMSF/接触/聚类或研究所需指标，报告重复、误差与采样限制。
领域验收：预测置信度不证明模拟体系正确；轨迹可生成不证明收敛，采样与统计验收依问题定义。
“对这一批化合物进行对接筛选，并分析候选相互作用。”
  1. 准备化学输入。核对受体状态、配体立体化学、质子化、电荷、金属/共价条件和目标区域。
  2. 选择对接协议。选择已接入的 Vina/GNINA 或适用大分子对接流程，设置盒子/约束/采样预算。
  3. 批量执行。数组任务或服务后端运行，保存各候选状态、种子、构象与评分，禁止静默丢弃失败样本。
  4. 分析与复核。通过 PLIP/几何和结构质量检查复核候选，检查空间冲突与协议适用性。
  5. 深入研究。在同一项目继续 MD、增强采样或自由能工作流，明确额外参数和统计要求。
领域验收：不同评分和协议不能直接混排，对接分数不能被报告为实验亲和力。
“把谱、指认和实验约束放在一起，完成结构计算与验证。”
  1. 数据导入。保存谱、峰表、序列和位移/约束，保留轴、单位、实验类型和指认关系。
  2. 处理与指认。连接 NMRPipe 等处理程序和 CCPN 等交互环境，人工选择作为可追踪节点。
  3. 结构计算。将经过校验的约束交给 Xplor-NIH 等适用部署，记录参数与随机重复。
  4. 集合验证。检查约束违反、几何、实验符合度和集合统计，保留不确定性。
  5. 整合扩展。SAXS/SANS 数据进入 ATSAS、RAW 或相应散射拟合操作；交联、HDX、EM 等数据经各自已验证的观测模型或约束适配器进入 IMP 等整合建模流程。每种输入的支持范围由具体操作声明。
领域验收：不同实验约束有不同误差与物理含义，不能自动转为未经验证的统一距离约束。
“实验室有一套脚本和软件流程，我希望在 NBDB 持续运行并让 Agent 使用。”
  1. 登记软件与依赖。导入脚本或连接已有服务，固定版本，确认环境、输入、输出和使用范围。
  2. 在项目中试运行。使用 Notebook/终端或注册操作，在受限资源中处理真实样本并检查输出。
  3. 形成可复用操作。发布 manifest、参数表单、收集器与验证档案，分配维护者和可见范围。
  4. 组合为工作流。连接其他已注册操作，显式加入转换和人工节点，保存工作流版本。
  5. Agent 调用。通过能力目录发现操作，按已声明范围组织任务，结果继续回到同一资产/证据系统。
领域验收：用户方法可以先作为探索性操作运行，再增加科学验证；不需要等平台开发者手写专门配方。

10 / PLATFORM ARCHITECTURE

统一平台技术架构

在现有 Vue + Spring Boot + MySQL 上增加科学应用控制层，建立独立执行平面与大数据平面。Python 是适配器与分析 SDK 的一种实现语言，底层同样可以运行 C/C++、Fortran、Java、R、MPI 和各类 GPU 软件。

优先复用已有软件体系

生态建议集成方式需明确的责任
Phenix / CCP4 等套件注册具体程序操作，也可将其已有流程接为 workflow backend。Phenix 官方已有结构解析 Agent，可评估作为领域后端。[P1]核对安装版本和许可；日志外发/模型配置由项目政策控制，NBDB 保存调用和结果谱系
RELION / CryoSPARC / Scipion支持原生作业或授权服务连接器，复用原有实验处理流程与元数据。[P2][P3][P4]指定一个调度权威；已由软件提交的子作业仅跟踪和对账，不由 NBDB 再重复提交
Nextflow / Snakemake / CWL复用成熟工作流定义，以外部工作流作业接入；先支持一种主引擎，再增加兼容适配。[P5]导入前校验数据类型、环境和权限；不能把格式可读取等同于科学验证通过
JupyterHub 与远程应用提供多用户交互会话与固定环境，接入平台项目授权和作业资源。[P6]用户代码与 Agent 自动工具分开授权；会话断线不等于计算终止
容器与 Slurm按站点条件使用 OCI/Apptainer/环境模块，配置 GPU/MPI 与文件系统。[P7]由集群管理员核对运行时、驱动和网络权限，不假设任意镜像能直接跨集群运行

现有 AI 搜索、用户、积分、检索与条目服务继续复用。新增目录、运行、资产、环境和会话模块，由平台 API 统一管理。是否采用 Kubernetes、独立消息队列或大型工作流引擎，依据实际部署与负载选择；通用性来自契约和执行接口。

11 / AGENT ORCHESTRATION

Agent 动态发现与编排

Agent 首先发现平台真实能力，再制定可执行计划。工具目录是能力事实源；固定工作流提供成熟经验，用户也可以指定任何已就绪的注册操作。

给 Agent 的平台能力接口

操作作用
capabilities.search按任务、输入类型和分子对象找工具/操作/工作流；返回适用范围、验证等级与来源。
operation.describe获取参数 Schema、必需输入、输出、资源、许可、可选部署和人工步骤。
deployment.resolve根据用户、数据位置和预算筛选当前就绪运行端；检查环境、数据库、模型权重、资源和授权。
plan.validate校验类型、选择对象、DAG、预算、科学前提和数据策略；必要转换必须显式列为节点。
runs.submit / inspect / cancel提交统一 RunSpec，查询真实状态、读取结构化日志摘要、请求取消。
sessions.request在需要人工判断时准备交互会话；用户完成后登记产物并继续后继任务。
artifacts.query / validate查取产物、计算与质量摘要，执行对应领域验证，再形成有证据的解释。

不同成熟度的工具如何参与

  • 已完成领域验证：可用于对应适用范围内的自动工作流，遵循项目预算和权限。
  • 已可执行但验证有限：提供专家模式、参数表单与清晰标签，Agent 只能按部署策略使用；运行成功不提升科学可信等级。
  • 已登记但无就绪部署：Agent 给出缺失环境/许可/数据库/资源清单，可以发起工具接入工单或选择已有适用替代；不能伪造执行结果。
  • 新工具与用户研究代码：在受控项目环境中接入和试运行，逐步形成操作契约和验证档案，无需为每个研究方法重写平台。

规划、执行、科学校验和报告保持不同职责。模型负责选方法和组织计划，程序处理参数与身份检查，软件执行计算，验证模块判断产物与科学前提。对复杂流程可接入已有领域控制器，NBDB 负责统一治理与结果归档。

有限自主性与持久化研究过程预算覆盖所有计划版本、并行分支和重试。Agent 可以在授权范围内修复格式、重试网络或调整允许参数；改变体系、采样目标、方法或外发目的地时，更新可见计划。长计算和交互期间 Agent 不必持续占用模型。

15 / RELIABLE EXECUTION

异步任务与集群可靠性

运行状态持久化到数据库，计算过程由独立 Worker 和执行后端管理。模型只在规划、必要解释和有限纠错时占用推理资源，长计算不持续占用一个聊天请求。

DRAFT → NEEDS_INPUT → READY → QUEUED → RUNNING → VALIDATING → SUCCEEDED
   └───────────────→ READY                         ├────────→ PARTIAL_SUCCEEDED
                                                └────────→ FAILED

非终态 → CANCEL_REQUESTED → CANCELED
人工检查点：RUNNING → WAITING_FOR_USER → VALIDATING / RUNNING
步骤 Attempt：PENDING → CLAIMED → SUBMITTED → RUNNING → COLLECTING → VALIDATED
                                                         └──────→ FAILED / TIMED_OUT

状态机为设计草案；NEEDS_INPUT 可在任务启动前或需要明确选择的检查点进入。Run、Step 与 Attempt 分开记录；终态转换使用版本号与条件更新，避免取消和完成相互覆盖。

可靠性要求设计方式验收行为
任务重复提交请求 Idempotency-Key 在用户/项目范围唯一；提交内容哈希一致时返回原 Run，内容不同则报冲突。重复点击、网络重发不会重复排队或重复预留积分。
累计预算与并发同一 Run 的预算覆盖全部计划版本、并行步骤和重试 Attempt；每次提交前原子预留剩余额度，重规划不能重置上限。预留失败不提交作业；取消中或后端失联时保留待对账额度，确认消耗后才结算或释放。
步骤执行与租约数据库条件领取、租约、心跳和 fencing token；消息/领取按“至少一次”设计，结果提交校验尝试版本。过期 Worker 的迟到结果不能覆盖有效尝试。
服务或 Worker 重启保存执行后端 job ID 和提交令牌；重启后查询实际作业状态。提交前后故障通过令牌与调度器记录核对。能够继续收集运行中作业，或明确判定丢失；不能无条件重新提交昂贵计算。
取消与超时先设取消请求、阻止新步骤，再调用后端取消与清理；确认终止后标记 CANCELED。独立设置请求、排队和计算超时。取消后不启动后继步骤；界面能区分“请求取消”和“已终止”。
产物原子登记产物先写临时位置，完成校验和哈希后登记最终引用；数据库事务发布有效产物，残留文件由清理任务处理。下游步骤只能读取完整且验证通过的输入。
部分成功与失败按配方区分必需步骤和可选增强。必需科学结果缺失则失败或部分成功，报告显示缺口。不能因为文字报告生成成功而将无有效科学结果的任务标为成功。
结果缓存确定性操作使用输入哈希 + 对象选择 + 参数 + 工具/数据库版本 + 环境/种子构成缓存键；随机重复保留独立 Run 身份，按协议决定是否允许缓存；公共与私有缓存隔离。输入修订、编号选择或参数变化后不会错误复用旧结果。

CPU、GPU 和 Slurm 的统一执行接口

定义 submit(spec)、status(jobId)、cancel(jobId)、collect(jobId) 四个动作。按实际部署接入 CPU/GPU、容器、Slurm、外部服务与交互会话。使用固定提交模板、工具环境和资源档位，并在作业目录写入结构化结果，避免将自然语言日志作为正式计算结果。

模型资源和分析资源分别调度复用现有按需模型服务经验，但将推理队列、轻量 CPU 分析和高内存图计算分开。Slurm 作业到达最长运行时间后可能终止，应使用可恢复的步骤和外部持久化产物，不把现有短时模型租约直接作为全部分析的运行时。

外部服务不支持取消时，只能停止后续处理并继续对账，界面不能标记远端已终止。检查点恢复由连接器声明；大型数据阶段、交互会话和授权席位均纳入状态与用量账本。

17 / MODELS & CONTEXT

模型、检索与上下文

模型策略：先评测现有服务，再决定升级

先使用现有模型服务验证配方选择、参数提取、结构化计划、中文科学解释和工具结果引用。通过模型网关屏蔽协议差异；必要时区分低成本意图解析、复杂规划和最终解释的模型配置。引入外部模型服务时，必须按照项目的数据外发设置处理输入。

模型选型的实测维度

  • 工具选择和 Schema 合法率。
  • 对多链、残基映射、装配体等概念的理解。
  • 缺证据时是否承认无法判断。
  • 中英文任务的一致性、上下文负载与延迟。
  • 同等正确率下的成本、并发与部署条件。

微调与多 Agent 的引入时机

先收集人工纠正的计划、工具轨迹和科学解释错误。若主要问题来自缺工具、缺数据或不明契约，应先补齐这些部分。只有在可测量的稳定错误上，才评估微调、专门路由模型或独立复核模型的收益。

把四类检索明确区分

检索类型适合回答需要声明的范围
结构化目录查询按实验方法、物种、日期、质量或条目关联筛选；可用于有定义的精确集合统计。过滤条件、索引更新时间、权限范围、分页与完整性。
语义与全文检索将自然语言描述转成候选条目或文献。候选上限、召回策略和截断；top-k 结果不能代表全库数量。
序列检索查找相关序列、构建体和可能模板。identity、覆盖率、E-value、数据库快照和分子类型。
结构检索寻找几何/折叠相似候选，开展结构近邻分析。查询链/域/复合物范围、工具模式、比对覆盖与评分定义。

RAG 主要用于方法手册、配方说明、质量指标解释和论文证据；数值分析通过计算工具完成。后续迭代 可增加文献连接器，保存 DOI / PMID、检索式和获取范围。只获取摘要时，应将依据标记为摘要，不能编造全文方法或图表结论。

项目记忆与上下文管理

长期保存研究目标、已确认的物种/isoform、对象选择、用户参数和有效产物引用。每次送入模型的是当前任务摘要、相关 Schema 和小规模证据包；大坐标、大表格、密度图和完整日志留在资产层，通过受限工具查询局部内容。模型生成的摘要可辅助检索，但不能覆盖正式科学状态。

图片输入的合适定位继续支持从论文图或截图提取标签、PDB/EMDB 编号、图注线索，再用数据库核实。仅凭渲染外形无法可靠识别蛋白或完成三维相似性判断；需要结构坐标时，应请求对应文件或经过核实的公开数据。

能力目录检索：Agent 按需加载操作 Schema、当前部署和验证范围，避免把全部工具文档写入一个超长提示词。工具说明用于生成候选，服务端契约与实时探针决定实际可执行性。

18 / GOVERNANCE

权限、许可与开放研究

统一平台从基础设计上同时支持注册工具与开放研究环境。运行身份、项目数据、外发、资源、许可和结果发布由服务端管理，使更多工具能够可靠接入。

控制对象实现要求
项目与数据权限所有目录可执行性、Run、会话、事件、缓存、存储挂载和下载执行对象级授权；私有资产与公共依赖隔离。
软件来源与环境使用受控构建、版本锁和探针；每个连接器声明可执行程序/函数和参数。研究者自定义环境先在项目范围试运行，发布共享时增加审核与验证。
Notebook / 用户脚本用户可在项目授权环境探索；隔离计算身份、目录、网络与资源。保存代码、依赖和产物，不能把探索代码自动当作已验证工具。
许可与并发席位逐版本登记适用场景、机构资格、服务器/服务部署和再分发条件；许可席位作为调度资源。凭证以引用方式注入运行端，不进入模型或普通日志。
跨站点与外发明确数据和日志是否发送到外部服务或嵌套领域 Agent；新目的地按照项目授权处理，支持指定环境内执行。
文件、进程与资源按文件类型检查真实格式、解压大小和解析上限；按工具隔离进程/环境、限制 CPU/GPU/内存/时间/存储，保护主站。
模型与来源数据网页、文件标题、论文和日志属于数据，不能改变运行权限；Agent 提交的是结构化工具请求。自定义代码运行需要独立且明确的用户授权。
产物与分享报告文本转义，前端使用受控查看器；下载/公开分享由用户决定；删除按原始数据、派生结果和备份生命周期执行。

已授权预算内的工具执行可以自动推进，无需每步重复确认。超过预算、首次外发或公开成果等实际变更向用户说明具体影响。对暂时缺资源或许可的工具，目录保留状态与接入路径，平台架构无需缩小支持范围。

平台级验收指标

  • 领域覆盖：逐域展示 M0/M1/M2/M3/M4 的操作与工作流数量，列出缺口，不将登记软件计入可执行能力。
  • 工程可靠性：关键权限、取消、重复提交、预算与重启对账用例全部通过；已验证操作的最小参考任务持续回归。
  • 科学可信：主要定量结果可追溯；封存参考任务中的已知关键对象/单位/证据错误为零，发现新错误阻断受影响版本。
  • 任务质量：按领域和验证范围统计完成率、专家可接受率、失败原因及分母；建议以各域 ≥90% 为初始讨论目标，基准后校准。
  • 复现：确定性任务按预定义容差重放；随机模拟、预测与采样按协议、重复和统计量评估；人工任务标明可重放范围。
  • 研究效率：记录数据搬运、环境准备、等待、计算和人工步骤时间，衡量用户在平台完成研究的比例。

工具数、操作数、验证范围和自动化工作流数分别报告。精确阈值随工具和研究协议制定；任何整体平均分都不能掩盖某一领域尚未可用或存在关键科学错误。

环境独立配置，公共依赖复用

不同软件采用各自镜像、锁定 Conda 环境、HPC 模块或授权服务，保留 CPU 架构、GPU、MPI 和库约束。预测权重、序列索引、力场和参考数据单独版本化，按站点预置；不能将几十种科学软件强行安装进主站或一个统一 Python 环境。

资源与计费模型

资源预估 = 工具操作 + 输入体量 + 参数/重复/窗口数量 + 部署性能
运行账本 = CPU核时 + GPU卡时 + 内存/时长 + 数据传输
         + 存储/保留 + 交互会话 + 许可/API费用（若适用）
项目预算 = 所有步骤 + 并行分支 + 重试 + 交互 + 暂存/传输预留

提交前原子预留，运行后按已公布的产品规则结算；后端失联或取消未确认时保留待对账额度。任务提交幂等与科学结果缓存是两个机制：随机模拟默认不因参数相同就合并为同一个结果，独立重复必须保留独立身份。

现有 AI 搜索文字/图片固定积分可继续使用，科学计算另设清晰的资源/配方价与预算上限。先通过不同领域真实样本测量资源，再决定服务器和存储容量；轻量坐标分析的成本不能外推到原始电镜数据、长模拟和多节点任务。

可观测性与运行维护

从平台 Run 追踪到外部任务、Slurm ID、会话和各项产物，区分排队、数据搬运、计算、人工等待与验证。监控目录健康、依赖版本、许可席位、孤立作业、GPU/IO/存储、预算和验证回归；软件升级通过新部署灰度，保留旧版本重放能力与备份恢复演练。

工期与团队的估算方式

先安排 2–3 周进行工具/授权/数据盘点和跨类型接入试验，再据此估算底座和工具包。具备现成集群与平台工程人员时，可把 8–12 周作为“首轮通用底座和代表性运行链路”的讨论窗口；随后按季度增加领域覆盖。该窗口不代表几十种软件、全部版本和全部科学流程都已验证完成。

建议核心团队包含平台后端/任务工程、科学软件与 HPC 工程、前端/可视化和测试运维等 4–6 个全职角色，再由各领域专家持续参与方法与结果验收。工具接入工作可以按领域并行；已存在环境的单一 CLI 包装，与多节点实验流程/商业服务/复杂 GUI 的工作量需要分开测算。

首轮演示的用途选择几何分析、GPU 模拟、原始数据处理、外部授权软件和交互应用作为平台底座样板。它们证明平台承载不同工具的能力，不构成平台只服务这些分析的产品限制。

23 / RISKS & DECISIONS

关键问题与立项定位

平台的长期覆盖目标保持完整；风险通过统一接入、资源、验证与维护机制处理。

主要问题平台应对
软件多、环境冲突软件与操作独立环境；驱动/MPI/数据库/权重形成依赖目录；用标准连接器持续扩展。
接入数量掩盖科学成熟度按操作和部署统计 M0–M4，区分目录、可执行和已验证流程；每个领域保存真实基准。
工具能运行但不能连用科学类型系统检查身份、单位和伴随文件；转换操作显式化，不只匹配扩展名。
复杂专业判断被误当全自动保留人工与交互节点；研究者可指定方法和参数，Agent 清楚说明已完成与待检查部分。
许可、商业托管或外部服务条件逐版本/机构登记资格与部署范围；许可席位参与调度，在有权限的运行端执行。
算力、IO 与成本差异巨大任务画像、数据就近调度、资源档位、配额、预算与真实样本测量；统一账本区分费用来源。
重复任务、检查点或远端状态不明执行后端对账、提交令牌、幂等费用、检查点兼容检查；远端不支持取消时准确显示状态。
持续维护成本每个领域包有维护者、版本策略、验证和回归；复用成熟套件/流程，优先维护真实高频操作。

开工前的必要盘点

收集现有集群与存储、已安装软件与授权、各领域常用流程、实际用户数据和方法需求、可用维护人员。以工具操作和执行模式建立接入矩阵，然后并行开发平台底座和领域包。当前本地 NBDB 的用户、AI 搜索、目录与积分可复用，科学计算平台部分需要按本方案新增。

本次方案的最终定位NBDB 承载结构生物学各种分析工作的执行与管理；Agent 将这些已经存在或持续新增的软件能力组织起来。核心交付是“统一平台 + 可运行工具生态 + 工作流与交互 + 智能编排”，首批工具和配方只决定建设顺序。
