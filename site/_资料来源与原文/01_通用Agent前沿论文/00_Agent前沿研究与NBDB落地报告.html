先给结论：该学习什么，先建设什么

你的目标是让结构生物学分析在 NBDB 内真正运行。论文选择因此要围绕“工具能否接入、任务能否完成、结果能否验证”展开。

01

最值得直接借鉴

统一工具契约、专业软件交互环境、可恢复的工作流、结果溯源，以及真实输入驱动的评测。这些能力可以在使用现成模型时建设。

02

需要针对领域重做

结构对象与残基映射、文件语义、GPU/集群作业、密度图与轨迹、局部质量，以及结构结果的解释边界。

03

有条件再投入

专用调度模型、强化学习和自动能力演化。前提是已有稳定执行环境、真实轨迹和可信的验收规则。

核心判断

近期研究越来越重视模型之外的运行环境、工具组织、状态、数据和评测。对 NBDB 而言，这意味着先让科学软件成为可执行、可组合、可验证的平台能力，再持续改进 Agent 的选择与控制能力。此处是对所选工作的综合判断，并非某篇论文的单独结论。

建议第一轮精读 Agent Rosetta ↗、ToolUniverse ↗、SciToolAgent ↗、Paper2Agent ↗、SciAgentGym ↗。前四篇解释工具与软件环境怎样组织，第五篇帮助定义多步任务怎样验收。

06 / RESEARCH TO PLATFORM

任务执行：从一次调用走向长流程

Agent 能选对工具，只完成了第一步。平台还需要管理作业排队、运行、中断、恢复、产物和质量。

专业软件应有清晰的动作与反馈

Agent Rosetta ↗的启发是：环境需要把复杂软件能力整理为可控动作，把冗长日志变成可定位的问题和质量摘要，并提供回退路径。对于 Phenix、Rosetta、GROMACS 等不同软件，动作设计和科学前提也不同，不能只套同一段提示词。

执行器决定“怎么运行”，Agent 决定“下一步做什么”

层责任关键记录
Agent / 规划层解释目标、选择方法、安排依赖、根据结果调整目标、候选方法、决策理由和停止条件
工作流层校验输入、安排并行、等待长作业、处理重试节点状态、依赖、检查点和预算
执行层按资源要求调用 API、CLI、脚本、Notebook 或 GUI命令/请求、环境、作业 ID、退出码和日志
验证层检查产物、科学前提、数值及质量变化验收结果、警告、失败原因和证据位置
已创建→输入检查→等待资源→运行→产物验证→完成 / 需修复

独立的结构质量统计和相似结构检索可以并行；依赖拓扑和参数化结果的模拟必须等待前置任务。重试时先判断输入是否有效、失败是否暂时、重复执行是否会产生副作用。长作业应返回任务标识并持续记录状态，用户关闭页面后还能恢复。

人机共享状态也要版本化

Tau2 Bench ↗提示我们，用户共同操作环境会增加难度。NBDB 中若用户在三维查看器改选链、删除配体或更换结构，Agent 下一步应读取新的场景和数据版本。每项分析绑定其使用的选择快照，避免把旧计算结果误贴到新结构上。

IPIGuard ↗提供另一类执行边界：外部论文、日志或网页内容应作为数据处理，工具权限及计划修改由平台规则控制。MAST ↗则提醒，多 Agent 交接必须明确目标、文件和完成条件。

NBDB 应先积累什么

每次运行保存输入哈希、实体映射、工具与环境版本、参数、任务事件、模型调用、产物、质量指标、错误分类和专家反馈。成功与失败都要保存。原始事件不可被“记忆总结”覆盖。

科研奖励需要多层条件

格式正确→工具适用→参数与单位正确→作业完成→产物有效→科学质控通过→目标得到合理回答。这些维度应分别记录。任何“未读真实输入却给出漂亮报告”的行为都不能获得成功标签。

开放科学任务常有多种合理路线，不宜把唯一工具序列作为标准答案。精修可以改善几何却损伤局部密度拟合；对接得分变好也不等于真实亲和力提高。训练前先把这些验收规则做成离线评测，确认分数与专家判断一致。

评测方案：证明它完成了真实分析

以下是为 NBDB 提出的评测设计，不是论文现成结果。优先借鉴 SciAgentGym、ScienceBoard、AstaBench、DSGym 与 OpenAgent 的问题意识。

首版任务族示例科学验收重点
输入检查与编号映射PDB/mmCIF、缺失残基、替代构象与序列对应链、模型、残基和处理规则正确
几何与质量二级结构、暴露面积、空间冲突、局部几何数值与参考流程一致，缺失与异常分开
结构检索与比较限定结构域的叠合与相似检索原子集合、覆盖率、对齐区域正确
界面与配体接触、氢键、埋藏面积、配体邻域对象、单位、阈值和定义正确
预测与对接候选生成、输入约束、构象比较产物有效，评分解释符合适用范围
动力学与轨迹周期边界、RMSD/RMSF、聚类与接触变化拓扑匹配、单位、参考系与分析区间正确
实验数据与模型cryo-EM、晶体学、NMR 分别建子集数据模型配对、局部与全局验证正确
多结构与变异批量比较、变异定位、界面与构象变化编号一致，控制混杂，不越级推断功能

把执行成功和科学正确分开

退出码为 0、文件存在且可解析，只能证明执行完成。还要检查结构身份、分析对象、编号、单位、方法前提、数值与解释。数值容差应按具体方法设定；随机算法需要种子或预先规定的统计验收规则。关键任务由固定参考流程和领域专家校准。

建议从 240 个真实实例起步

8 类各 30 个：每类 10 个开发、5 个验证、15 个隐藏测试，共 80 / 40 / 120。按蛋白家族、结构来源和工作流模板分组后切分，把近重复结构留在同一组。隐藏集预留至少 40 个多步工作流、30 个边界或故障案例，标签可重叠。这是可调整的建设起点，具体规模按专家成本决定。

维度怎么测避免的误判
真实数据接地同题替换结构；同结构换文件名；重算报告中的关键数值背模板也能得高分
长流程检索→准备→计算→验证→可视化→报告，定位第一处错误与污染只统计最后一句“成功”
恢复能力注入排队、超时、中断、缺文件、工具失败盲目整链重试掩盖问题
工具变化schema、输出字段、版本和可用性变化；允许查新文档静态基准通过就认为能适应新工具
稳定性每个隐藏任务独立运行 5 次，报告均值和 pass^5把5次至少成功1次当稳定成功
公平性固定输入、工具、资料、预算和评分器资源更高的系统看似更聪明
建议记录的指标

工具选择与参数正确率、执行率、科学验收率、可复现率、恢复率、pass^5、CPU/GPU 用量、模型费用、总耗时及重试次数。pass^5 指一个任务的 5 次运行全部成功；它不同于 pass@5“多次尝试至少一次成功”。

第一版发布门槛可讨论设为：工具契约检查全部通过，隐藏测试执行率 ≥95%、科学验收率 ≥90%、pass^5 ≥80%。这些是建议工程门槛，必须经过任务难度与专家校准后确定；各任务族单独报告，平均分不能掩盖薄弱类别。错误链、错误单位、虚构计算或把未运行作业报告为完成，应列为必须修复的问题。

不同论文中的成功率不能直接横向排行：模型、工具访问、任务集、预算、评分器和尝试次数常常不同。本报告保留任务规模等必要背景，不拼接一张跨基准“最高分”榜。
