隔离权限与数据治理：让Agent只能做被允许的事

模型可能读到不可信论文、网页、工具描述和日志；科研数据又常包含未公开对象与受限资料。成熟落地需要把“模型建议执行”与“系统有权执行”分开，并让数据在检索、计算、追踪和分享全过程遵守同一权限。

01 / THE PROBLEM

从一个具体问题开始

一个能调用任意命令、读取整个共享盘、携带长期凭据的Agent，会把一次文本误判放大成系统操作。仅在提示里写“不要泄露”，或仅在前端隐藏项目，都无法构成数据访问控制。这里给出的措施是分层设计，不代表能够消除所有提示注入或隔离风险。

来源或角色可参与什么不能自动获得什么
用户与研究合同确定目标、输入与接受标准执行器服务账号的全部权限
论文、网页、检索与文件内容提供待核对的研究信息修改工具权限、执行任意命令或泄露数据
模型与计划节点提出候选动作和参数绕过合同、配额、隔离或审批规则
工具与Worker执行授权范围内的具体操作访问整个数据空间或改变验收规则
独立验证器按固定版本生成判定覆盖原始证据或将未知改为通过
02 / IMPLEMENTATION & BOUNDARIES

怎样实现，为什么这样分工

01

资料提供信息，不能自行取得指挥系统的权限

给内容标记来源和信任边界：用户授权的任务、应用规则、检索到的原文和工具返回分别处理。论文中的命令、网页的操作建议、日志中的文本都先作为待解释数据；它们不能直接改变工具权限、数据可见范围或发布目标。检索相关性也不意味着内容可信。

工具调用要经过模型之外的策略检查：当前用户是否有权使用该工具、访问这些对象、向该目标写入，参数是否在允许范围。即使模型返回格式正确的调用，也必须通过这些检查。提示分隔、检测器和模型防护可以降低部分风险，但无法代替执行端授权；防护测试应观察是否真的越权，而不只看回答是否包含可疑语句。

具体例子

结构文件附带说明要求将结果发往新地址时，系统保留说明作为来源内容；导出操作仍以用户已有授权、目标白名单及项目策略为依据。

02

把工具权限缩小到对象、动作和时间

将读取、计算、修改、分享与删除分成不同能力。科学计算worker只获得当前任务所需输入的读取权和专用输出位置的写入权；模型服务、资料检索和调度服务不共享一个万能凭据。凭据由执行端按身份获取，尽量不进入模型上下文、普通日志或产物目录。

授权检查覆盖任务创建、异步执行、结果下载和分享链接，而不只检查第一跳API。长期排队的任务在真正执行时重新核对关键权限；权限被撤回后，已有作业和产物怎样处理由明确策略决定。使用数据库行级策略可作为一层约束，但表所有者等特殊角色可能绕过通常规则，因此不能把启用某功能写成完整租户隔离证明。

03

执行隔离需要同时限制文件、网络与资源

工具适配器优先调用经过审查的固定入口与类型化参数，避免把模型文本直接拼成命令。任务使用独立工作目录，只挂载必要输入；按需要限制网络出口、CPU、内存、进程数、磁盘和执行时间。资源上限既防止误用，也保护共享科研集群免受失控循环影响。

容器有利于打包依赖和应用部分隔离控制，但容器共享宿主内核，权限、挂载和守护进程配置仍会改变风险。允许执行未知代码的场景需要更强的隔离方案和专门评估，不能沿用可信科学工具的权限模板。进程终止后还要清理临时目录、凭据与网络授权，并处理可能仍在运行的远程作业。

04

科研数据治理覆盖派生物、索引、追踪和备份

输入文件进入系统时登记所属项目、共享范围、保留规则与来源约束。派生产物继承必要的数据分类和访问限制；检索索引、缩略图、缓存和模型追踪中的片段也属于数据副本。对外部模型或观测平台发送什么内容，应在数据路径设计时确定，并支持只发送元数据或脱敏摘要。

删除请求需要沿血缘找到活动数据、派生物、缓存、索引和分享权限。备份通常有独立的保留与恢复周期，应记录实际删除边界和过期过程，而不是承诺即时擦除所有历史副本。审计记录保留谁、何时、基于什么身份做了什么及结果，不默认保存所有敏感原文；审计访问本身也受权限与保留策略约束。

05

把代码和工具升级当作供应链变更

工具登记除名称和说明外，还应包含源码与构建来源、环境摘要、许可证、维护责任人、允许动作和测试结果。固定版本与镜像摘要可以识别实际运行的内容；构建来源和验证记录有助于追查内容从哪里来，但不能单凭一个摘要证明软件无漏洞或方法正确。

新依赖、新MCP服务和新的工具描述都先在隔离环境评估，并通过兼容性、权限与回归检查后才进入可发现目录。撤回有问题版本时保留被影响Run和Artifact的关联，重新判断哪些结果需要重验。安全维护的交付物应包含威胁模型、权限矩阵、数据流图和升级记录，使后续维护者知道边界为什么这样设置。

03 / DESIGN DECISIONS

把技术选型写成有条件的判断

工具能否直接获得共享盘访问权？
本参考设计：按任务挂载必要输入与独立输出目录。

为什么：缩小一次错误调用可触达的数据和文件范围。

何时调整：确有跨任务数据需求时，通过受控数据服务表达查询与权限，而不是开放整个目录。

是否把完整原文与结构数据写入追踪平台？
本参考设计：默认记录身份、摘要和必要定位；内容采集按数据类别配置。

为什么：追踪能帮助排错，也可能制造额外的数据副本和外发路径。

何时调整：经项目授权且保留、访问和删除规则清楚时，启用有范围的内容记录。

容器能否作为所有代码的唯一隔离边界？
本参考设计：根据代码可信度和环境风险选择隔离等级。

为什么：可信工具、用户脚本和未知代码具有不同攻击面。

何时调整：开放动态代码执行或外部扩展时，先升级隔离与测试，再开放能力。

04 / FAILURE WALKTHROUGH

用故障检查设计，而不只看正常流程

设计推演，用来暴露状态和责任边界；并非本站的真实事故记录。

触发情形

系统读取了含有越权操作指令的外部资料，并据此提出读取另一项目文件和导出数据。

容易发生的处理

因该资料来自检索结果、调用参数也合法，就认为操作得到用户授权。

有依据的处理

执行端以当前身份、项目边界和目标策略拒绝调用，保留最小审计证据；阅读任务可继续，但该资料不能扩展工具能力。随后将此案例加入越权回归测试。

应留下的证据：检查授权决定、对象标识、调用目标与实际外部操作；不能仅因模型说“已拒绝”就认定数据没有被读取或发送。
05 / DELIVER & VERIFY

读完后应能交付什么

  1. 有资料信任边界与端到端权限矩阵。
  2. worker凭据、目录、网络与资源按任务收敛。
  3. 跨项目访问与权限撤回场景有真实检查。
  4. 日志、缓存、索引和备份纳入数据保留规则。
  5. 工具升级可追溯并能定位受影响结果。

06 / PRIMARY REFERENCES

回到官方资料核对机制与版本

OWASP · LLM Prompt Injection Prevention ↗

支持对不可信内容、工具行为、最小权限与监控进行多层控制；不把单一提示或检测器描述为完备防护。

Docker Engine security ↗

容器隔离涉及内核、控制组、权限、守护进程与配置，不能仅凭使用容器宣称完整隔离。

PostgreSQL · Row Security Policies ↗

行级策略可约束数据行访问，但默认行为及所有者等特殊角色的边界需要单独理解。

SLSA v1.2 specification ↗

构建与源码来源证明用于提升供应链可追溯性；本文没有声称采用某条记录即达到SLSA等级。
