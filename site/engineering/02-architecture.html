参考架构与数据模型：让结果能够解释、恢复和追责

参考架构的价值在于明确谁决定、谁执行、谁保存事实、谁判断质量。组件数量可以少，但这些边界及其关联必须清楚，才能从单人原型走到多人共享服务。

01 / THE PROBLEM

从一个具体问题开始

许多原型把聊天记录当作数据库，把临时目录当作产物仓库。模型一旦重试、浏览器断开或Worker重启，系统就无法解释某个文件属于哪次尝试，也无法判断重跑是否会重复消耗资源。成熟落地需要独立于模型上下文的业务事实和数据血缘。

01Task / 任务

用户接受的研究问题与合同版本

02Run / 运行

一次执行选择与环境快照

03Step / 步骤

计划中的逻辑操作

04Attempt / 尝试

这一步的一次实际执行

05Job / 外部作业

调度器可查询的实际工作

06Artifact / 产物

带摘要、选择和来源的文件

07Validation / 判定

依据某个验证器版本作出的结论

关系本参考设计的约束
Task → Run → Step → Attempt各层可有多个子记录；重新尝试不覆盖旧记录。
Attempt → Job此处以0或1个外部作业为例；更复杂的复合作业需另建映射。
Job → Artifact作业可以没有产物，也可以产生多个产物；退出成功不证明文件有效。
Artifact ↔ Validation一次判定可覆盖一组产物；同一产物可被不同版本验证，不覆盖历史。
02 / IMPLEMENTATION & BOUNDARIES

怎样实现，为什么这样分工

01

控制面与计算面分开理解

控制面接收请求、核对权限与任务合同、编译计划、决定路由并汇总状态；计算面运行解析、几何分析或其他科学工具，可能位于本地进程、容器Worker或HPC队列。两者通过版本化操作与产物引用交互。模型不应拥有整个共享计算环境的隐式控制权，科学程序也不应依赖对话窗口存活。

这一分层不要求立即建设微服务。早期可在单个服务中使用API模块、工作线程和数据库；当长作业、不同依赖或资源隔离需要出现时，再拆出Worker。先解决可追踪性，避免同时引入多种消息系统、编排器和数据库却没有清晰责任人。

02

用实体关系表达一次计算，而不是一个总状态

Task保存用户目标和合同修订；Run固定某次方案、模型/提示版本及总体预算；Step表示依赖图中的一次逻辑操作；Attempt表示这一步的某次实际尝试。外部Job保存调度器身份、资源请求和观测状态，Artifact保存文件身份、摘要、存储位置与生产者，Validation保存检查器版本、判据、测量值和判定。

这些实体不能简单一一对应。一次Step可能因失败有多个Attempt；一次Attempt可能提交多个分片Job，或只运行本地函数而没有Job；一个输入Artifact可以被多个Run复用。输出文件与验证结果分开保存，因为相同文件可以在新验证规则下重新检查，而不必篡改原始执行事实。

具体例子

说明性关联：Task T1 → Run R1 → Step S2 → Attempt A2 → 外部Job J8 → Artifact F9；Validation V3检查F9，并引用原合同、验证器版本及判据。每条箭头都应有数据库外键或可核查引用，而不是只写在模型生成的报告中。

03

区分三种状态与三类存储

业务状态回答任务是否被接受、等待什么及能否发布；执行状态回答进程或外部Job是否运行；科学状态回答产物是否满足领域判据。数据库保存身份、关系和状态；文件或对象存储保存原始产物与日志；追踪系统帮助定位耗时和调用。追踪记录通常有采样与保留策略，不应成为唯一的业务账本。

LangGraph的checkpointer保存线程图状态，store保存跨线程应用数据；它们可支持Agent运行，但项目仍需定义任务、作业和产物的事实来源。图状态、数据库元数据与外部调度器状态出现差异时，应有核对程序，不能让某一段对话自动覆盖外部事实。

04

在数据库与消息之间保留可靠交接

如果“写入已接受任务”和“发送执行消息”分开完成，崩溃可能造成任务已显示接受却永远没有计算。可把任务与待发事件写入同一数据库事务，再由dispatcher转发事件，称为transactional outbox。消费者根据稳定操作身份去重，状态更新使用条件检查或版本号，避免晚到消息覆盖新状态。

outbox解决的是数据库记录与待发送事件的一致性，不会把数据库和Slurm提交合成一个分布式原子事务。事件仍可能重复，作业提交仍可能出现结果未知；下一章的执行账本和恢复核对负责处理这段间隙。每个一致性保证都要说明覆盖的边界。

05

数据血缘要能回答“这个结论由什么产生”

产物登记建议保留原始输入摘要、派生关系、工具及环境版本、参数、生产Attempt、随机种子（若适用）、质量检查和访问范围。大文件可只在数据库保存引用与摘要；正式发布的报告应引用固定版本，而不是一个会被覆盖的latest路径。摘要用于核对字节身份，不等于内容科学可信。

W3C PROV用实体、活动与参与者描述来源，这里借用其思想建立最小血缘链，无需第一天就实现完整本体。目标是研究者能从报告追到验证、文件、实际执行和原输入；更换工具、修复算法或撤回某个输入时，也能找出受影响的下游结果。

03 / DESIGN DECISIONS

把技术选型写成有条件的判断

是否一开始就拆成很多服务？
本参考设计：先保留明确模块和持久接口，按资源、故障与部署边界逐步拆分。

为什么：微服务增加运维与一致性成本，不能代替数据模型和业务保证。

何时调整：独立扩缩容、不同科学环境、集群接入或故障隔离成为实际需求时。

聊天历史能否作为唯一状态？
本参考设计：正式状态进入业务账本；模型只读取与任务相关的状态视图。

为什么：对话会截断、压缩或重写，无法可靠表达外部Job、重复尝试和不可变产物。

何时调整：纯问答无需外部作业时可简化实体，但仍应保存输入与引用来源。

文件存在后就写任务成功吗？
本参考设计：先登记文件身份，再独立写入验证记录，依据合同产生可发布状态。

为什么：文件写入、验证完成和报告发布是不同事件，混在一起会把部分结果误报成功。

何时调整：检查规则更新时新增Validation版本，原始Artifact和历史判定保留。

04 / FAILURE WALKTHROUGH

用故障检查设计，而不只看正常流程

设计推演，用来暴露状态和责任边界；并非本站的真实事故记录。

触发情形

API已经提交“任务接受”事务，却在发送队列消息之前崩溃；用户只看到长时间排队。

容易发生的处理

让用户重新提交，生成另一份无法关联的任务；原任务继续悬空。

有依据的处理

从同事务保存的outbox恢复投递，按操作身份消费；再由账本核对任务、消息和执行状态。

应留下的证据：任务ID、待发事件ID、投递尝试、消费者去重结果及状态版本应能够关联；outbox转发本身不声称消除了所有外部重复。
05 / DELIVER & VERIFY

读完后应能交付什么

  1. 关键实体、基数、状态写入者和事实来源有文档。
  2. 进程重启后仍能从持久记录重建用户看到的任务状态。
  3. 报告能够反查到固定输入、执行尝试、产物与验证器。
  4. 数据库备份与文件保留策略覆盖同一业务恢复点。

06 / PRIMARY REFERENCES

回到官方资料核对机制与版本

事务把数据库内多步更新作为原子操作；不等于同时控制外部调度器。

AWS Prescriptive Guidance：Transactional outbox pattern ↗

处理数据库与事件通知的双写问题；事件可重复，消费者需要幂等处理。
