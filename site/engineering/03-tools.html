工具工程与科学计算执行：从能调用到可维护能力

工具不只是模型能看见的函数说明。可上线的工具需要明确合同、运行环境、资源、错误与产物，并能在真实后端持续验证这些声明。

01 / THE PROBLEM

从一个具体问题开始

一份教程中能运行的科学程序，换到多用户服务器后可能遇到依赖冲突、GPU/内存不足、输入数据不可见、许可证条件变化或输出格式变动。如果只是把命令包装为工具，Agent会把环境故障和科学失败混为一谈，长期运行也难以升级。

01

声明

知道工具接受什么输入、产生什么输出。

02

可用

执行环境健康，版本与资源能被核对。

03

跑通

参考任务真实执行，错误和产物能回收。

04

验收

新输入满足相应领域判据，能力范围有证据。

工具注册只是第一层。协议接入、科学workflow与HPC调度分别解决不同问题。

02 / IMPLEMENTATION & BOUNDARIES

怎样实现，为什么这样分工

01

为每个工具维护一张能力合同

工具目录至少说明标识与版本、适用任务、输入输出类型、前置条件、资源类别、运行环境、超时、错误类别、验证方式及支持范围。不要把README里的“支持结构分析”直接变成广泛能力声明；应具体到格式、数据规模、对象选择和测试过的任务。注册可发现、环境可运行、任务能完成是三个不同状态。

工具的可用性由持续探针和小型回归任务确认。环境健康检查回答二进制和必要资源是否可用；功能检查验证参考输入能否得到可解析产物；领域检查验证结果与参考或不变性质是否一致。维护者应能禁用某个有问题版本，避免Planner继续选择它。

02

Adapter隔离模型接口和科学程序接口

adapter把类型化请求转成受控参数或配置文件，准备输入、启动程序、收集退出状态、解析输出并生成规范化结果。模型只选择公开参数，不应靠自由拼接shell字符串来决定路径、环境或权限。外部软件的输出格式变化可以在adapter中处理，不要求所有上游Agent都理解这些差异。

adapter既保留便于程序消费的结果，也保存原始日志与输出引用。错误应区分输入无效、对象不存在、依赖不可用、资源不足、超时、程序异常、产物损坏和领域检查失败。工具不得用一个泛化的“请重试”掩盖这些差别，也不要在解析失败时用模型补出一个看似合法的数值。

具体例子

说明性工具边界：请求包含固定输入Artifact、明确原子选择与单位；adapter返回execution状态、输出Artifact列表、解析摘要和错误类别；Validation另存。执行成功但覆盖不足时，应保留计算结果及不通过的检查，不能把failed直接改写为success。

03

根据实际计算形态选择运行后端

短小、依赖简单的解析可在受限Worker内执行；需要独立依赖的工具可使用容器；长时间、GPU或多节点任务交给已有调度器。所有后端实现同一逻辑操作合同，但保留各自能力差异：本地进程取消、容器资源回收和HPC作业取消并不具有相同接口或时延。

在Slurm中，sbatch成功表示控制器接收脚本并分配Job ID，并不表示资源已获得或科学计算已完成；官方还说明除脚本本身外并不替用户搬运文件。因此提交前要验证集群能访问输入、临时目录与输出位置，提交后保存集群身份和Job ID，后续查询队列及记账记录。

04

把资源和排队时间作为计划的一部分

为工具设置经测量或保守估计的CPU、内存、GPU、临时磁盘、运行时长与并发上限；由服务策略映射到允许的partition和账户。排队等待与实际运行分开计时，资源请求超出范围应被拒绝或明确升级，不能让模型无限增大资源重试。单次预算还应覆盖失败尝试与产生的大文件。

轮询调度器应合并请求、限制频率并退避；squeue官方特别提示避免程序高频循环制造控制器RPC压力。作业从当前队列消失不意味着失败，可能需要查看sacct历史；记账是否启用及保留多久依赖集群配置。状态未知应显式保留，而不是自行猜测终态。

05

环境可重建，升级可验证

固定工具提交或发布版本、依赖锁、容器镜像摘要、配置及输入数据版本；还要记录影响数值的硬件/驱动或外部数据库条件。Apptainer定义文件可记录构建环境和测试，但“用了容器”不等于已覆盖所有宿主依赖，也不自动保证每次数值逐位相同。可重复性应按实际接受容差验证。

工具上线前核对软件与数据的获取、运行和分发条件，并保存对应版本的许可信息；这是项目资产管理步骤，不能把所有GitHub仓库都当作可自由商用。新版本先跑参考、边界与失败任务，对比产物schema和科学判据，再切换工具注册；已有Run继续引用原版本。

06

四种编排各有职责，已有科学流程可以作为复合工具

Agent编排决定如何依据观察选择下一步；业务持久执行保存任务状态并处理等待与恢复；科学workflow表达数据依赖、计算步骤和环境；资源调度器决定作业何时在哪些资源上运行。LangGraph、Temporal、Nextflow/Snakemake与Slurm分别可在这些层承担职责，但不应据此给每层都部署一套新系统。

已有稳定科学流程时，可把经验证的Nextflow或Snakemake流程包装成复合工具，让Agent提交合同内的输入与参数，再收集流程身份、产物和失败记录。这样可复用既有依赖管理与执行能力；上层仍要核对对象、权限、预算与科学验收，不能把pipeline完成等同于研究结论成立。

03 / DESIGN DECISIONS

把技术选型写成有条件的判断

本地函数、容器还是HPC？
本参考设计：根据依赖、资源、时长和现有基础设施选择后端，共用上层操作合同。

为什么：模型工具接口不应暴露每个集群的零散提交细节，但适配层要保留真实后端状态。

何时调整：资源需求、隔离要求或任务规模变化时增加后端，不把每个工具强行塞进一种执行形态。

怎么确认工具已接入成功？
本参考设计：分别记录已注册、环境健康、参考任务通过与领域支持范围。

为什么：可调用目录和真实运行能力之间存在依赖与质量验证缺口。

何时调整：工具或数据升级、部署节点变化后重做对应探针与回归。

OUT_OF_MEMORY是否直接无限重试？
本参考设计：按受控资源升级策略、尝试上限和总预算处理，保留原失败。

为什么：相同条件重试可能只重复浪费；自动扩大资源也可能挤占共享集群。

何时调整：实测资源画像支持新的合理请求，且仍在该用户与任务的授权配额内时。

04 / FAILURE WALKTHROUGH

用故障检查设计，而不只看正常流程

设计推演，用来暴露状态和责任边界；并非本站的真实事故记录。

触发情形

sbatch已返回Job ID，但任务停留PENDING；前端把“提交成功”显示为“分析完成”。

容易发生的处理

报告尚未生成的科学结论，或因用户等待而再次提交同一计算。

有依据的处理

展示已接收与排队原因，分别记录等待和运行时长；关联Job ID继续查询，只有收集产物并完成相应验证后才报告计算结果。

应留下的证据：提交回执、队列状态及原因、资源请求、输入可见性、最终退出信息、实际产物摘要和验证记录。
05 / DELIVER & VERIFY

读完后应能交付什么

  1. 每个工具有维护者、版本、支持范围和验证任务。
  2. 适配层能明确返回执行失败、产物失败与领域检查失败。
  3. 至少验证一次目标后端的输入输出路径、资源限制与取消行为。
  4. 升级不会覆盖旧产物或悄悄改变既有Run的工具身份。

06 / PRIMARY REFERENCES

回到官方资料核对机制与版本

Slurm：sbatch ↗

sbatch接收并分配作业ID不代表立即开始；除脚本外不负责搬运用户文件。

Slurm：Job State Codes ↗

区分PENDING、RUNNING、COMPLETED、OUT_OF_MEMORY、TIMEOUT等调度状态。

Slurm：squeue ↗

队列状态和原因查询；官方提醒避免高频循环造成RPC负载。

Slurm：sacct ↗

作业与步骤的记账数据取决于配置，可查询状态和退出码等。

Apptainer：Definition Files ↗

定义文件记录构建与运行相关配置，%test支持按项目需要设计容器检查。

Nextflow：官方文档 ↗

Nextflow采用数据流模型描述可扩展的计算流程，支持本地、HPC与云执行平台；本手册建议将已验证流程封装成受控复合工具。

Snakemake：官方文档 ↗

Snakemake以规则定义可复现分析流程，并提供执行插件、环境管理与报告；本手册将其职责与Agent决策及资源调度区分。
