F20 / ARCHITECTURE & IMPLEMENTATION REVIEW
开发框架架构资料与源码入口核对

Semantic Kernel

Semantic Kernel把模型服务、应用函数与插件纳入可组合SDK，是理解企业Agent集成的历史入口。官方当前将Microsoft Agent Framework定位为其继任方向。

01 / COMPONENT VIEW

核心抽象：每层究竟负责什么

01

Kernel与服务

Kernel组织模型服务和应用功能。服务适配负责调用协议，应用仍负责数据含义、错误和任务完成判据。

02

Plugin与Function

插件将已有函数交给模型或应用调用。函数描述与类型是入口，真实业务行为、外部状态和领域验证由实现承担。

03

Agent与迁移

Agent和协作能力随语言与版本演进。阅读旧代码时固定版本，再对照官方迁移指南，而不是机械替换包名。

02 / RUNTIME VIEW

沿一次任务，从输入追到实际交付

  1. STEP 01

    应用注册模型服务与可用插件。

  2. STEP 02

    任务进入Agent或相应调用流程，选择并执行函数。

  3. STEP 03

    函数结果回到模型或业务控制层。

  4. STEP 04

    应用验证交付结果，再记录迁移实现与旧版本行为的差别。

03 / STATE & DEPLOYMENT

系统状态、执行环境和失败边界

数据、状态与恢复

插件依赖、模型上下文、业务数据与Agent状态需要独立生命周期。跨语言序列化和异常形式也需要对照测试。

部署形态与依赖

Python、.NET等语言绑定与模型服务各有依赖。当前继任框架和旧SDK的包、样例与托管模式应分别固定。

工程取舍

便于将既有应用函数纳入Agent，但更换运行框架后并不自动保持状态、协作和错误语义，需要行为回归。

04 / SOURCE READING

源码阅读：从具体入口进入实现

从Kernel和函数接口阅读，连接到具体语言绑定，再按官方迁移指南核对新的Agent与工作流对象。

已核对的源码入口函数或类型线索读代码时回答什么
python/semantic_kernel/kernel.py ↗Kernel沿一次输入追到输出，标出执行边界、状态和可测试条件。
dotnet/src/SemanticKernel.Abstractions/Kernel.cs ↗参考文件中的接口与数据结构沿一次输入追到输出，标出执行边界、状态和可测试条件。

入口文件已按目录核对并读取内容；函数/类型线索为静态提取，不代表已运行全部代码。 阅读链接固定到所记录提交。

  1. 先看最小示例的输入、工具和返回值，建立对象对应。
  2. 沿入口追一次真实调用，区分模型决策、程序执行与外部状态。
  3. 再读测试与错误路径，确认接口合同和版本限制。
05 / PRACTICE & DECISION

用小任务检验是否适合，而不只记住功能名

一个与课题相关的练习
本导读建议，非原项目实验

把一个只读结构检查函数作为插件，再写出迁移后的同等工具接口；比较参数、返回值及失败行为。

练习交付物要证明什么
任务合同输入、输出、对象、接受标准及必要依赖明确。
运行与产物记录真实操作、状态和文件来源可追溯，失败不会伪装成成功。
独立检查报告实现了什么、什么未通过，哪些结论仍受证据限制。
