I01 / ARCHITECTURE & IMPLEMENTATION REVIEW
基础设施架构资料与源码入口核对

MCP Python SDK

MCP标准化Agent应用与工具服务的交互。它解决工具发现、调用和资源访问的协议问题；模型决策、计算调度和科学验收仍属于应用及领域系统。

01 / COMPONENT VIEW

核心抽象：每层究竟负责什么

01

Server与能力声明

服务端暴露工具、资源或提示等能力，描述输入输出。声明是调用合同，必须与真实软件环境和支持输入一致。

02

Client与传输

客户端连接服务、发现能力并发送调用。传输与协议错误要同工具业务错误分开，避免将连接失败误当科学结论。

03

结构化返回

返回内容和状态供调用方继续决策。返回可解析不代表对象或数值正确，服务端和调用方应分别保留验证记录。

02 / RUNTIME VIEW

沿一次任务，从输入追到实际交付

  1. STEP 01

    客户端连接指定服务并发现工具。

  2. STEP 02

    应用按任务和类型选择工具，发送参数。

  3. STEP 03

    服务执行真实操作并返回内容或错误。

  4. STEP 04

    应用绑定任务与产物，再执行科学检查。

03 / STATE & DEPLOYMENT

系统状态、执行环境和失败边界

数据、状态与恢复

协议会话、工具调用和外部Job是不同状态。异步科学任务应设计提交、查询与结果收集接口，不依赖对话文字推断完成。

部署形态与依赖

本地stdio、远端HTTP等配置按所用协议和SDK版本核对。当前Python SDK主分支已演进，旧版FastMCP示例与新接口不能混用。

工程取舍

统一接口降低跨客户端接入成本，但不能自动提供领域Schema或资源管理。单进程少量工具也可直接函数调用，不必为协议而增加部署。

04 / SOURCE READING

源码阅读：从具体入口进入实现

先读官方SDK服务端/客户端示例，再看工具Schema、传输和错误处理；把协议合同与科学合同分别写清。

已核对的源码入口函数或类型线索读代码时回答什么
src/mcp/server/mcpserver/server.py ↗Settings、lifespan_wrapper、MCPServer、require_client_extension服务接口、消息、任务状态和产物分别怎样表达？
src/mcp/client/client.py ↗Client服务接口、消息、任务状态和产物分别怎样表达？

入口文件已按目录核对并读取内容；函数/类型线索为静态提取，不代表已运行全部代码。 阅读链接固定到所记录提交。

  1. 先看最小示例的输入、工具和返回值，建立对象对应。
  2. 沿入口追一次真实调用，区分模型决策、程序执行与外部状态。
  3. 再读测试与错误路径，确认接口合同和版本限制。
05 / PRACTICE & DECISION

用小任务检验是否适合，而不只记住功能名

一个与课题相关的练习
本导读建议，非原项目实验

把同一个结构检查函数直接调用和经MCP调用各运行一次，比较参数、错误类型与返回结果是否一致。

练习交付物要证明什么
任务合同输入、输出、对象、接受标准及必要依赖明确。
运行与产物记录真实操作、状态和文件来源可追溯，失败不会伪装成成功。
独立检查报告实现了什么、什么未通过，哪些结论仍受证据限制。
