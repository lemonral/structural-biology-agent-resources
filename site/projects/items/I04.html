I04 / ARCHITECTURE & IMPLEMENTATION REVIEW
基础设施架构资料与源码入口核对

Temporal Python SDK

Temporal为持久工作流和活动执行提供运行体系。关键概念是可重放的控制逻辑与具有外部副作用的Activity分开；它不是科学计算调度器的替代品。

01 / COMPONENT VIEW

核心抽象：每层究竟负责什么

01

Workflow与历史

Workflow表达控制关系，运行依赖历史事件恢复。代码演进与确定性要求影响已有任务能否安全重放。

02

Activity与Worker

Activity执行外部I/O或计算，Worker承接实际工作。活动重试可能再次发生，外部作业必须有核对和去重设计。

03

超时、重试与取消

这些规则管理长任务失败和生命周期。心跳或取消信号需要活动与外部软件配合，不能由配置自动证明科学任务已停止。

02 / RUNTIME VIEW

沿一次任务，从输入追到实际交付

  1. STEP 01

    提交业务工作流并持久记录输入。

  2. STEP 02

    Worker执行Activity，必要时向集群提交作业。

  3. STEP 03

    活动持续查询外部状态或报告进度，工作流推进后续处理。

  4. STEP 04

    失败后依据历史恢复，核对真实作业与已有产物再决定重试。

03 / STATE & DEPLOYMENT

系统状态、执行环境和失败边界

数据、状态与恢复

工作流历史、Activity尝试、调度器Job和科学产物各有身份。持久执行不等于外部系统自动exactly-once，也不等于科学质量合格。

部署形态与依赖

需要Temporal服务、Worker及实际工具或集群连接。为研究原型可先使用本地开发服务和短任务，逐步验证恢复语义。

工程取舍

适合小时级任务和跨服务流程，但引入服务、Worker和工作流版本管理成本。短小确定步骤不一定需要独立持久工作流平台。

04 / SOURCE READING

源码阅读：从具体入口进入实现

从Workflow、Activity、Worker三层阅读官方样例，重点理解重放与实际副作用的边界。

已核对的源码入口函数或类型线索读代码时回答什么
temporalio/activity.py ↗defn、Info、ActivityCancellationDetails、client、in_activity沿一次输入追到输出，标出执行边界、状态和可测试条件。
temporalio/worker/_worker.py ↗PollerBehaviorSimpleMaximum、PollerBehaviorAutoscaling、Worker、WorkerConfig、WorkerDeploymentConfig沿一次输入追到输出，标出执行边界、状态和可测试条件。

入口文件已按目录核对并读取内容；函数/类型线索为静态提取，不代表已运行全部代码。 阅读链接固定到所记录提交。

  1. 先看最小示例的输入、工具和返回值，建立对象对应。
  2. 沿入口追一次真实调用，区分模型决策、程序执行与外部状态。
  3. 再读测试与错误路径，确认接口合同和版本限制。
05 / PRACTICE & DECISION

用小任务检验是否适合，而不只记住功能名

一个与课题相关的练习
本导读建议，非原项目实验

用模拟长计算测试失联、活动重试和取消；再让恢复逻辑先查询既有Job，证明不会仅因没收到确认就重复提交。

练习交付物要证明什么
任务合同输入、输出、对象、接受标准及必要依赖明确。
运行与产物记录真实操作、状态和文件来源可追溯，失败不会伪装成成功。
独立检查报告实现了什么、什么未通过，哪些结论仍受证据限制。
