Purpose, status and product unit

The product turns a natural-language structural-analysis question into an executable scientific task with explicit objects, constrained parameters and independent acceptance. Its unit is the task, frozen specification, Run and evidence bundle; a chat message is an input or explanation surface, not the authoritative execution record.

This is the English edition of the proposed PRD 0.2 and current contract baseline. Publishing these documents does not deploy an Agent. The existing AdK offline teaching package performs four real coordinate operations under a fixed plan without a real model. The policy exercise covers synthetic/mock decisions, not real authentication, sandbox isolation or distributed quotas. Neither establishes open-ended planning or cross-family generalization.

Researchers need reviewable results; tool maintainers need versioned capability packages; scientific reviewers need provenance; operators need budgets, permission boundaries and recoverable state. A usable first release must complete one real, inspectable scientific task and preserve its failures as well as its results.

P0 boundary and long-term task space

General-purpose means that new scientific capabilities enter through versioned contracts, adapters, validators and reference tests. P0 is a bounded CPU coordinate-analysis slice; broad task maps are the extension goal, not a claim that every method is already installed or validated.

Task familyP0 commitmentLater extension, separately accepted

Mapping and superpositionSupported protein Cα selections, explicit one-to-one mapping, separate fit/evaluation sets, RMSD/displacementsComplex correspondences, domains, retrieval and multi-structure comparison
Geometric contactsExplicit heavy-atom objects, atom pairs and residue summariesSASA/buried area, richer interface methods and condition-aware statistics
Quality and experimental supportInput/object/numerical integrity onlyGeometry, confidence and experimental map/model validation as distinct capability packages
Trajectories and ensemblesRecognize unsupported input and explain requirementsTopology/PBC/units/sampling contracts, convergence, uncertainty and ensemble analysis
Prediction, docking and designNo P0 claim to run these methodsVersioned adapters with license, resource, applicability and independent acceptance evidence

P0 excludes arbitrary shell or generated code, software installation, unrestricted URLs or data export, original-file overwrite, real Slurm/GPU submission, distributed multi-Agent control, de novo biological design and wet-lab operation. It must identify unsupported goals and explain a feasible next step without fabricating tool output.

The workbench shows project identity, supported scope and tasks. The task view separates conversation, real object inventory, candidate/frozen specification, plan, budget and state. The results view separates execution from scientific status and shows all Attempts, mapping/metric plots, evidence and download. An administrative view controls capability and model availability; a front-end role label never authorizes access.

One Run, one frozen scientific contract

  • Create immutable original TaskRevision and authorized input references. Preallocate ANALYZE Run and reserve its cumulative budget before model work.
  • Run fixed registered PREFLIGHT inspection, then model interpretation and necessary clarification. MODEL and allowed PREFLIGHT Attempts may precede a frozen specification; ordinary scientific TOOL Attempts may not.
  • Programmatically freeze FrozenTaskSpec once before scientific computation. It defines objects, selections, mapping/method intent, units, outputs and acceptance policy.
  • Ask the model for PlanCandidate; compile references, types, DAG, scientific preconditions, allowed tools, access and remaining budget. Persist the immutable accepted plan before dispatch.
  • Restricted Workers execute actual operations and publish verified immutable artifacts. Independent validators assess scientific quality. The controller may make bounded same-contract PlanRevisions using real observations.
  • Generate an evidence report or explicit rejected/inconclusive outcome. Record parsing, clarification, repair, execution and reporting costs under this same Run.
  • A post-freeze change in scientific goal, object, selection or method creates a linked new TaskRevision and Run. Old history, costs and UNKNOWN effects remain; ordinary retries do not become new independent evaluation samples.

Clarification resolves scientific intent. Approval controls an exact high-impact side effect. They are different workflows. Already authorized normal parsing, computation, new immutable reports and same-permission downloads proceed automatically.

Implementation and entity ownership

Use one source repository and one LangGraph controller, a PostgreSQL business ledger and a restricted CPU Worker. API, controller and compute processes may restart independently. A React/TypeScript workbench and FastAPI/Pydantic contracts are proposed implementation choices; adapting the front end must preserve API and scientific contracts.

Use Gemmi for structural inventory and a tested NumPy numerical kernel behind versioned adapters. The Bio.PDB teaching implementation is a migration/reference comparison, not a second default production parser. Low-throughput scheduling initially uses database transactions, leases and an outbox; Redis/Celery/Kafka are not P0 requirements.

Store graph checkpoints separately from authoritative business facts, even if both use PostgreSQL. LangGraph checkpointing cannot guarantee exactly-once external side effects. The Worker requires read-only input mounts, dedicated outputs, no host secrets/control sockets, restricted network and enforced CPU/memory/process/disk/time limits. Verify these controls on the target environment.

    Creation/update requests bind an Idempotency-Key to principal, project, method, resource and canonical payload digest. Identical key plus payload reuses identity; changed payload conflicts. Recheck current authorization even when returning a cached response. Use expected revision/state version for compare-and-swap updates.     State, budgets and uncertain execution

    AxisStates / interpretation
    SpecificationDRAFT, NEEDS_CLARIFICATION, FROZEN, DISCARDED. Only a frozen checked scientific contract authorizes ordinary scientific TOOL work.
    Run phaseINSPECTING, SPECIFYING, PLANNING, EXECUTING, VALIDATING, REPORTING. Phase is independent from execution status.
    ExecutionQUEUED, RUNNING, WAITING_INPUT, WAITING_APPROVAL, RECONCILING, CANCEL_REQUESTED, UNKNOWN, COMPLETED, FAILED, CANCELLED.
    ScienceNOT_EVALUATED, VALIDATING, ACCEPTED, REJECTED, INCONCLUSIVE, NOT_APPLICABLE. Completion and acceptance must both hold for verified scientific delivery.
    PolicyNOT_CHECKED, ALLOW, DENY, REQUIRES_APPROVAL. ALLOW applies to the action and says nothing about its scientific truth.

    Reserve cost/resource capacity atomically before each action; settle actual use afterward and retain unknown liabilities. Resume, retries and replanning share the Run budget and deadline. Persist operation identities and request digests before dispatch. Lease expiry initiates reconciliation; a late Worker needs the current fencing epoch to publish. Checkpoints restore a program position, not an external process fact.

    CANCEL_REQUESTED is an intent. Only confirmed termination and cleanup justify CANCELLED. If submission or completion cannot be determined, retain UNKNOWN and block dangerous resubmission. Temporary artifact slots, checksum/size checks and immutable metadata publication must recover from a crash between file write and database commit.

    CapabilityChecks requiredInterpretation boundary
    InspectionActual format, hash, model/entity and chain namespaces; residues, insertion codes, altloc and excluded species.Parsing success is not full structure-quality validation.

    Evaluation, optimization and denominators

    The north-star metric is scientifically valid delivery: preallocated in-scope valid-task Runs whose actual artifacts pass independent scientific checks, whose report matches evidence and whose actions were authorized, divided by all preallocated valid-task Runs. Failures, timeouts, missing artifacts and false refusals stay in the denominator. Retries are Attempts, not fresh independent Runs.

    Separately report ambiguity handling, unsupported/invalid handling, critical hidden errors among delivered results, unnecessary clarification/approval, actual unauthorized side effects, complete cost and latency. Unknown billing is UNKNOWN with coverage. Separate cold and warm caches and show per-family difficulty and object coverage.

    DatasetUseBoundary
    D_devVisible development labels and debuggingPrompt/tool optimization may reuse this set; record source and authorization.
    D_regKnown defects and representative valid casesPassage establishes known regression coverage, not held-out generalization.
    D_testSealed acceptance after configuration freezeSplit correlated objects, families and templates as clusters; hide references/scorers from retrieval and memory.
    D_feedbackQuarantined user feedback and online failuresCheck license/privacy, reproduce and scientifically review before promotion to the next dev/reg version.

    The starting proposal is a 24-task pilot across at least four public object families, followed by 60 frozen acceptance tasks: 36 explicit valid, 12 ambiguous and 12 invalid/unsupported, spanning at least six families separated from development. Three preallocated real-model Runs per task are suggested subject to budget. These are starting design choices, not power guarantees or achieved results.

    ConfigurationQuestion answeredImportant limit
    Q-REFCan fixed checked TaskSpec and known valid plans produce correct reference artifacts?A deterministic executor does not demonstrate natural-language planning.
    Q-BASEHow does a minimal registered-tool real-model Agent perform with the same tools, knowledge, scope and total budget?Retain hard safety and final scientific checks; do not make unsafe output the baseline.
    Q-CANDDoes the proposed compiled-task and bounded-repair system improve usable delivery, hidden errors, false refusals and cost?If multiple mechanisms change, attribution is to the complete system; test individual mechanisms separately.

    Score objects, numerics, artifacts and permission facts with deterministic checks and independent references. Use anchored expert rubrics for interpretation. An LLM judge may assist only after task-specific expert calibration; it does not establish numerical truth or authority. Compare paired tasks, aggregate repeats within task and estimate uncertainty by independent object clusters. With too few clusters, present descriptive results and the limitation.

    Proposed release goals are ≥90% valid-task scientific delivery overall and ≥80% within each declared family; ≥95% appropriate ambiguity/boundary handling; and zero observed known severe hidden errors or unauthorized effects in tested samples. These are draft goals to calibrate after the pilot and freeze before final testing, not measured claims. Never lower them after inspecting final failures and call the old protocol passed.

    Security and human control

    Untrusted publications, tool output and logs are data, not instructions with authority. Server sessions, project membership, registered capabilities and current policy determine action scope. Validate each execution boundary; a model statement that it refused is not evidence that no file was read or transmitted.

    • Keep secrets in approved server connectors, outside prompts, ordinary logs, URLs, reports and artifacts. Apply project data policy independently to model requests, traces, indexes, caches and exports.
    • P0 permits normal new immutable outputs without approval and disables unsupported high-impact actions. P1 approvals bind exact action data, destination, parameters, versions, actor/project, expiry and nonce; revalidate current authority and consume atomically.
    • Use restricted fixed tool entry points. Filesystem path containment must handle symlinks and races; do not rely solely on lexical checks or a container label.
    • Escape report content, keep raw HTML downloads isolated, authorize every artifact fetch and avoid private-file existence/size leaks through range requests.
    • Handle revocation, cross-project references, malicious retrieved instructions, quota races and late Worker messages in real integration tests.

    Nonfunctional requirements and operations

    Initial limits are configurable development proposals: 50 MiB upload, 100 MiB output per Run, 12 registered tool actions, 8 model calls, 2 transient retries per step, 2 scientific-repair rounds, 2 GiB Worker memory, 300 s CPU tool wall time, 900 s Run wall time and 2 concurrent CPU Runs per project. Calibrate/version them on the actual server. They are neither measured capacity nor universal scientific-tool limits. Reject unsupported archives and oversized data rather than silently truncating the object.

    Candidate P95 request acceptance/query latency ≤2 s excludes model inference and scientific completion. State the hardware, workload, window and denominator before adopting an SLO. Use actionable alerts for stalled recovery, queue age, missing artifacts, unknown cost and scientific-check regressions. Preserve business events independently of optional sampled traces.

    Backups must restore metadata and immutable bytes together in an isolated drill. Release code, image digests, model/prompt settings, schemas, tool versions, validators and reference data as a compatible set. Canary a bounded cohort, stop on critical science/security regressions and preserve in-flight versions. Rolling back new Runs must not blindly reissue old side effects.
