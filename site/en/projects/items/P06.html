OpenHands

Connect Agent Canvas to execution services while separating UI from runtime behavior.

Agent workbench and execution-service product architecture

Source snapshot: 2026-10-30 · Chinese original

1. Position in the system

In the reviewed architecture, OpenHands/OpenHands primarily provides Agent Canvas, with services, tools and sessions in software-agent-sdk. Understanding repository boundaries is necessary for an accurate system model.

Best fit
Learning how workbenches, agent services, workspaces and event streams form an execution product.
Boundary
The UI repository does not contain every runtime component. Scientific calculations and HPC adapters need backend implementations.
Relation to other systems
The reviewed OpenHands repository hosts Canvas; software-agent-sdk hosts Agent Server, tools, sessions and execution.

2. Mechanism at a glance

  1. Interact through the workbench
  2. Connect to Agent Server
  3. Manage tools and execution through the SDK
  4. Present events and results

Components and responsibilities

ComponentResponsibility
Canvas and interaction stateThe workbench presents conversations, files and events while managing client state. Visible progress does not represent every service-side fact.
Agent Server adapterThe API adapter handles server configuration, compatibility and events. It exposes contracts relevant to disconnects and version mismatch.
SDK and automation boundaryThe SDK owns runtime semantics; scheduling and automation live at another boundary. Separate when execution starts, what it runs and how it is presented.

3. Follow a real run

  1. Select an execution service and submit a task in Canvas.
  2. Create or resume a session through the service API.
  3. Execute agents and tools on the service, returning events and artifacts.
  4. Present results while verifying backend facts and domain criteria independently.

State and recovery

Separate client stores, service sessions, tool events and workspaces. Browser disconnection does not imply cancellation; reconnect to the actual server state.

Deployment and dependencies

Workbench, Agent Server and optional automation services may be deployed separately. Establish component versions and interfaces before reusing older tutorials.

4. Tradeoffs and scientific use

Useful for execution-product service boundaries and interaction design. Copying the workbench does not supply a scientific backend, and cross-repository changes add compatibility work.

Structural-biology adaptation

Adapt task, file and execution-event presentation; add scientific tools and independent validators behind the interface.

Practice task

Simulate a long analysis, disconnect the UI and reconnect. Confirm progress, artifacts and failure states belong to the same server task rather than stale client memory.
