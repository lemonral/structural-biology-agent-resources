Temporal Python SDK

Separate replayable control logic from activities that perform external operations.

Durable workflow and activity runtime

Source snapshot: 2026-10-30 · Chinese original

1. Position in the system

Temporal provides durable workflows and activity execution. The core distinction is replayable control versus activities with real external side effects, with scientific schedulers remaining separate.

Best fit
Long-running tasks and cross-service processes with explicit recovery requirements.
Boundary
It does not replace scientific scheduling. Durability does not ensure exactly-once external execution or scientific quality.
Relation to other systems
Workflow histories, activity attempts, scheduler jobs and artifacts have separate identities.

2. Mechanism at a glance

  1. Persist workflow history
  2. Run activities through workers
  3. Handle timeouts, retries and cancellation

Components and responsibilities

ComponentResponsibility
Workflows and historyControl is recovered from historical events. Determinism and code evolution affect safe replay of existing tasks.
Activities and workersActivities perform I/O or computation and workers execute them. Retried activities can repeat, requiring external operation identity and deduplication/reconciliation.
Timeouts, retries and cancellationPolicies govern failures and lifecycle, but heartbeats and cancellation require cooperation from activities and external software.

3. Follow a real run

  1. Submit a workflow and persist its input.
  2. Execute activities, submitting cluster jobs where needed.
  3. Query external status or report progress while control advances.
  4. Recover from history, reconcile real jobs and artifacts, then decide whether to retry.

State and recovery

Distinguish workflow history, activity attempts, scheduler job IDs and scientific artifacts. Persistent execution does not establish external exactly-once behavior or valid science.

Deployment and dependencies

Requires a Temporal service, workers and actual tool or cluster connections. Prototype with a local service and short tasks to test recovery semantics.

4. Tradeoffs and scientific use

Useful for hour-scale and cross-service work, with added service, worker and version-management cost. Short deterministic tasks may not need this platform.

Structural-biology adaptation

Test a simulated long computation through disconnects, retries and cancellation, reconciling an existing job before resubmission.

Practice task

Simulate lost contact, activity retries and cancellation. Query an existing job before retrying, proving that missing acknowledgement alone does not cause duplicate submission.

Read workflow, activity and worker examples together, identifying replayable code and actual side effects.

Version and evidence boundary

This is durable-execution infrastructure rather than an agent framework or domain validator.
