Boundary

Relation to other systems
Read Letta Code separately from historical Letta V1 server tutorials and storage structures.

2. Mechanism at a glance

  1. Maintain memory and identity
  2. Reuse skills and delegate
  3. Continue across interactions and services

Components and responsibilities

ComponentResponsibility
Memory and contextMemory blocks and files carry mutable context. Separate observations, user facts, model inferences and revisable strategies.
Skills and subagentsReusable operations and delegation need applicability conditions, versions and failure records; one success cannot justify transfer to every object.
Interaction and servicesCLI, App Server and channels expose different entry points. Client state, server runs and memory storage remain separate layers.

3. Follow a real run

  1. Read task background from current context and memory.
  2. Select tools or skills and delegate when needed.
  3. Record observations and update memories under explicit rules.
  4. Reconcile changed data and tool versions before reusing experience in another session.

State and recovery

Version memory and retain its sources. Model-authored entries are not automatically facts; verified operating experience only applies under its documented conditions.

Deployment and dependencies

Use the reviewed implementation and its dependencies separately from the historical Python V1 server. Do not infer current deployment from obsolete API or storage paths.

4. Tradeoffs and scientific use

Continuity reduces repeated background input, but contaminated memory, stale knowledge and incorrect strategies can influence later tasks. Memories need inspection, correction and withdrawal.

Structural-biology adaptation

Retain verified operating experience with explicit applicability and provenance, while structural tools produce fresh evidence.

Practice task

Record a structure-file selection error as a conditional failure lesson. Change the task and verify that the system does not apply the lesson outside those conditions.
