DSPy

Improve language-model programs through signatures, modules, metrics and optimizers.

LM-program evaluation and optimization

Source snapshot: 2026-10-30 · Chinese original

1. Position in the system

DSPy separates a language-model program’s structure from its optimization. Developers define task interfaces, modules and evaluation targets, then improve configurations with development data. It is not a cluster-job runtime.

Best fit
Programs with declared input/output semantics, composable modules and explicit optimization metrics on training or development data.
Boundary
Domain constraints, external job state and independent scientific validation are not supplied by the optimizer.
Relation to other systems
Compare by system responsibility. Program optimization occupies a different layer from an agent runtime or cluster scheduler.

2. Mechanism at a glance

  1. Define modules and metrics
  2. Generate candidate programs
  3. Evaluate and select

Components and responsibilities

ComponentResponsibility
SignaturesDeclare semantic inputs and outputs so the same task can be compared across prompts or model configurations without hiding every stage in one prompt.
Modules and compositionRepresent prediction, retrieval or agent capabilities and connect them in Python. Test module outputs against downstream requirements.
Metrics and optimizersSearch candidate configurations using a defined metric and development set. Faulty metrics can select undesirable behavior, making independent verification and data splits essential.

3. Follow a real run

  1. Fix task signatures and a replayable tool environment.
  2. Prepare development samples and an independent scoring function.
  3. Compare candidate programs and select a configuration against the metric.
  4. Freeze the program and test unseen objects and task combinations.

State and recovery

Save program structure, optimization data, metric version, models and tool environment, not only the final prompt. Keep development and frozen-test results separate.

Deployment and dependencies

Requires model access and repeatable evaluation. Include both tool and search costs. Validate the scorer before expanding optimization on scarce scientific data.

4. Tradeoffs and scientific use

Systematizes iteration without guaranteeing generalization. Leakage, metric gaming and tool-environment drift can invalidate apparent development improvements.

Structural-biology adaptation

Optimize a typed tool-selection program while keeping structural operations and independent scientific acceptance in controlled tools.

Practice task

Optimize structure-check tool selection on a development set, holding out new structures and malformed inputs. Report scientific acceptance, false rejection and cost alongside format validity.

5. Reading path

README and a minimal example, followed by Signature, Module and optimization entry points.

Follow Signature and Module into optimization code. Check candidate scoring, scorer independence and reproducibility of the frozen configuration.
