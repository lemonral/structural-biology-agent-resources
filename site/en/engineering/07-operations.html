What problem this chapter solves

A long-lived service must locate failures, reduce their impact and recover safely. Operational evidence should connect user requests, actual computation and scientific outcomes.

Use stable identities across asynchronous boundaries

Correlate request/task/Run/Step/Attempt/Job/Artifact/Validation with code, model, tool and release versions. Durable business events carry authoritative state transitions; traces and span links help diagnose timing across processes. Do not make an optional tracing platform the only place a task fact exists. Minimize raw sensitive content while keeping enough identifiers to find the first contract violation.

Define SLOs around the user promise

State the operation, denominator, window, measurement point and workload. API acceptance/query latency is different from queue wait, model inference and scientific completion. A suggested 99% or two-second illustration is not a measured target. Separate availability from scientifically accepted delivery, and report cost/unknown usage so fast failure is not mistaken for efficient service.

Alert toward an actionable response

Prioritize user impact and stalled recovery: old unknown jobs, missing artifact registration, exhausted reservations, queue age, scientific-check failures and authorization anomalies. Each alert needs an owner, initial containment, diagnosis and a recovery check. A CPU spike alone need not wake a maintainer unless it threatens a defined service boundary. Keep runbooks versioned with the affected system.

Demonstrate recovery through drills

Back up metadata and immutable artifact bytes with a consistency strategy. Restore into an isolated environment, inspect lineage and hashes, reconcile unfinished work and verify access boundaries. A successful backup log cannot establish a working restore. Test provider outage, disk full, Worker loss, acknowledgment loss and late results; record what is known, unknown and still consuming resources.

Release and cost control share a loop

Version model/prompt/tool/parser/checker/data settings with code and images. Evaluate a bounded cohort before expansion, and consider compatibility with in-flight Runs. Pause new work and reconcile existing executions when a release breaks state progression. Rollback must preserve versioned history and must not blindly replay old side effects. Include failed attempts, queueing and remote compute in the same cost ledger.

Failure scenario and response

Scenario: After a release, tasks stay “running” although external jobs have finished and users resubmit.

Response: Pause new submissions on the affected version. Reconcile Runs and Jobs, collect existing artifacts and validate them; recover only genuinely missing steps. Roll back only after checking compatibility with current in-flight state, then investigate duplicates and cost.

This is a design exercise, not an incident report from a deployed service. Confirm actual behavior from task, process/job, artifact and policy records rather than from the final text alone.

Delivery checklist

  • Request, Run, Job, Artifact and Validation can be located from each other.
  • SLOs identify windows, denominators and workload.
  • Alerts have owners and recovery checks.
  • Metadata and files have passed an isolated restore drill.
  • Releases protect in-flight state and rollback is tested.
  • Retry and remote-resource costs remain visible.
