What problem this chapter solves

Retrieved text, tool descriptions and logs are untrusted information. Scientific data may also be unpublished or restricted. Authority must follow authenticated identity and policy through every component.

Information does not acquire command authority

A paper, page or tool result may contain an instruction to access another project or export data. Treat it as content, not permission. The execution gateway validates the current principal, project, object, action, destination, tool version and budget. A model saying it refused is not proof that no access occurred; inspect the trusted side-effect ledger. Preserve legitimate task branches when an unrelated malicious action is rejected.

Narrow authorization by object, action and time

Mount only the inputs required by the task and use a dedicated immutable output area. Avoid broad shared-drive access or long-lived credentials in Workers. High-impact approval, when implemented, binds exact data hashes, destination, parameters, version, expiry and one-time use; it cannot enlarge hard rights or budgets. Recheck access after revocation and on cached reads, streams and downloads.

Restrict filesystem, network and resources

Use nonprivileged fixed tool environments with read-only inputs, scoped output and no host secrets or control sockets. Enforce CPU, memory, process, disk and time limits; restrict egress to the actual need. Container use alone is not a complete isolation claim. Unknown generated code has a different threat model from a tested scientific adapter and needs stronger isolation before it is offered.

Govern derived data as well as raw input

Indexes, model prompts, traces, caches, plots, reports and backups create further copies or paths of disclosure. Apply project classification, retention, access and deletion rules to all of them. Default telemetry should capture identifiers, hashes and minimal diagnostic locations rather than complete private structures or raw prompts. Any expanded content collection needs an explicit permitted purpose and retention boundary.

Treat upgrades as supply-chain changes

Pin source/build provenance and dependencies, review executable entry points and identify affected artifacts. A new tool, model, parser or image can change scientific behavior and security exposure. Re-run numerical, policy and regression checks before wider enablement. A provenance record is useful evidence, not a claim that an entire security standard has automatically been achieved.

Failure scenario and response

Scenario: A retrieved document asks the Agent to read another project and export its structures.

Response: The final execution boundary rejects the action using current identity, project and destination policy; it records minimal evidence and can continue the legitimate reading task. Add the actual blocked action to cross-project regression, not only a textual prompt test.

This is a design exercise, not an incident report from a deployed service. Confirm actual behavior from task, process/job, artifact and policy records rather than from the final text alone.

Delivery checklist

  • Trust boundaries and permission matrices cover the entire data path.
  • Worker credentials, directories, egress and resource rights are task-scoped.
  • Revocation and cross-project access are integration-tested.
  • Logs, indexes, caches and backups have retention rules.
  • Tool upgrades are traceable to affected scientific results.
