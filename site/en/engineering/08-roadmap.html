What problem this chapter solves

Progress by observable exit evidence. Neither more infrastructure nor more tool names establishes scientific maturity. The stages below are recommendations, not a fixed schedule or certification.

Stage 1: prove one scientific task independently

Choose one explicitly bounded task family with real inputs, a fixed-workflow baseline, an actual artifact and independent reference. Cover valid input, wrong selection and tool failure. Separate model, tool and environment responsibilities. A reviewer should be able to explain every result from original bytes to numerical check, and failures should remain failures.

Stage 2: turn a call into a task service

Add stable identities, persistent state, a restricted Worker, query/cancel/download and artifact registration. Exercise restarts and acknowledgment loss. Refreshing the UI must not compute again. Recovery should first find existing external work and artifacts, then decide what may safely continue. A graph checkpoint alone does not satisfy this stage.

Stage 3: discover gaps with a bounded real pilot

Use a small known user group, explicit project permissions, declared tasks and quotas. Run realistic negative inputs, recovery drills and support procedures. Freeze evaluation versions, track human interventions, explain unknown states and assign an owner. Broaden task families only when each has an adapter, validation protocol and demonstrated user value.

Stage 4: sustain delivery through change

Establish measured capacity and cost, SLOs, alerts, on-call/support responsibility, data lifecycle, backup restore, release evaluation and rollback. Preserve execution evidence across software/model/tool changes. State the tested scope and withdraw unsupported service claims when conditions change. A lasting service is an operational agreement backed by evidence.

Select components around reuse boundaries

One repository can keep clear API/controller/Worker boundaries. Split services when measured resource, fault or team constraints justify the extra network/version/permission overhead. Reuse a graph framework for bounded control, a typed contract library for shape checks, a real database for facts and specialized tools for science. Write down what each component does and what the application still owns: identity, scientific semantics, external-job reconciliation and independent acceptance.

Failure scenario and response

Scenario: Many tools have been added, but nobody can determine whether failures came from the model, tool version or environment.

Response: Return to representative frozen tasks. Repair contracts, state, raw execution records and validators, and assign failure ownership. Compare scientific delivery, diagnosability, intervention and total retry cost before adding more scope or roles.

This is a design exercise, not an incident report from a deployed service. Confirm actual behavior from task, process/job, artifact and policy records rather than from the final text alone.

Delivery checklist

  • Supported tasks, users and research value are explicit.
  • Each stage has deliverables, owners and exit evidence.
  • One trustworthy task family precedes indiscriminate tool growth.
  • Process, state and scientific ownership are clear.
  • Release review includes access, capacity, restore, rollback and support.
  • Component choices are checked on the same actual tasks.
