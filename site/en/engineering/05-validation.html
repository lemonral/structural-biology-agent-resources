Scientific acceptance and Agent evaluation

What problem this chapter solves

Judge execution, artifacts, science and interpretation separately. A system can run successfully and still answer the wrong scientific question.

Four acceptance gates

First, determine whether a real execution occurred under the expected adapter and environment. Second, validate artifact structure, completeness, identity and provenance. Third, check scientific prerequisites, mapping, units, numerical values and applicability. Fourth, check whether the report is supported by those artifacts and stays within the evidence. Keep all four outcomes; do not compress them into one success field.

Independent references and invariants

Prepare trusted numerical references, reviewed object selections and invariants before evaluation. Examples include internal-distance invariance under a rigid transform, known-transform recovery, right-handed fitting and separation of fit/evaluation regions. Tolerances are part of each tool contract, not arbitrary post hoc thresholds. Test the validator with positive, negative and boundary cases, including finite plausible values from the wrong chain.

Split tasks and objects to test generalization

Hold out related object families, near-duplicate templates and task combinations together. Freeze reference inputs, versions, mappings, labels and interpretation rubrics. Distinguish development, regression, final acceptance and quarantined feedback. Re-running AdK examples can show regression stability; it cannot establish generality across all structural biology. Include invalid inputs, ambiguity and unsupported requests, not just answerable tasks.

Freeze configurations and isolate mechanisms

Compare a deterministic scientific executor, a minimal real-model tool Agent and the proposed controlled system using the same tools, knowledge, model conditions, budget and stop rules where applicable. Keep hard safety and final scientific acceptance in every condition. Use single-factor or structured ablations for contracts, runtime feedback and repair, rather than changing many components and assigning all benefit to one.

Report denominator, cost and scope

Every preallocated Run receives an outcome, including missing artifacts and failed or falsely refused tasks. Retry cost belongs to the original Run. Mark broken references/scorers as evaluation-invalid and missing billing as UNKNOWN. Report scientific delivery, hidden errors, refusal quality, human intervention, cost and cold/warm latency by family and difficulty. Pair comparisons by task, aggregate repeated Runs within task and estimate uncertainty at an independent object-cluster level.

Failure scenario and response

Scenario: Both files parse and return a plausible RMSD, but one selection uses an unrelated chain.

Response: Object/mapping validation must reject trusted delivery. Preserve the candidate and diagnosis; if the intended selection changes the frozen scientific contract, create a linked new revision/Run. The failed original remains in evaluation and cost records.

This is a design exercise, not an incident report from a deployed service. Confirm actual behavior from task, process/job, artifact and policy records rather than from the final text alone.

Delivery checklist

  • Test tasks have frozen identities, families and independent references.
  • Execution, artifact, science and explanation outcomes are separate.
  • Validators are tested for false acceptance and false rejection.
  • Comparisons keep tools, resources and stop rules controlled.
  • Failures, retries, hidden errors and uncertainty are reported.
