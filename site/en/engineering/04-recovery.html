Durable execution and recovery under uncertainty

What problem this chapter solves

Disconnection creates uncertainty, not permission to repeat a side effect. Recovery starts with durable identities and reconciliation of what the executor actually did.

Separate logical operations from attempts

A stable operation identity represents a particular scoped intent and payload. An Attempt records an actual execution try. Retries may create new Attempts, but must preserve causal linkage and the same Run budget. Bind idempotency to authenticated scope and canonical payload, not just a user-supplied string. The same key with a different request is a conflict; an old key cannot bypass revoked access.

Write intent before submitting and reconcile afterward

Before an external submission, persist the intended operation and correlation key. If the scheduler accepts a job but confirmation is lost, use namespace, stable operation key and a bounded submission time window to find the original execution. This requires a backend that retains queryable correlation. If the original cannot be established, preserve SUBMISSION_UNKNOWN/UNKNOWN and escalate rather than assuming nothing happened.

A checkpoint restores software state, not the outside world

A replayed graph node may execute again. Before repeating any effect, consult the ledger and actual process/job/artifact state. Lease expiry alone does not prove a process stopped; a PID can also be reused. Use an execution handle, start-time evidence, output slot and fencing epoch to stop stale Workers from publishing over recovered state. Persist state transitions with optimistic or transactional concurrency control.

Use different responses for different failures

Clarify invalid/missing scientific input; bound retries for safe transient faults; disable and repair an unavailable environment; retain scientific rejection when the output fails its contract; keep uncertain external effects unresolved until reconciliation. Cancellation intent is not termination. A Worker or backend must confirm the terminal process state and cleanup before resources can be fully settled.

Validate cache reuse

A cache key must represent input bytes, selections, scientific parameters, code/environment versions and relevant policies. Recheck current authorization and artifact integrity. A cached result may have been scientifically validated under an old checker; append a new validation where required instead of overwriting history. Never share a cross-project hit solely because the content digest matches.

Failure scenario and response

Scenario: An external job was accepted but its acknowledgment was lost; the Worker then restarts.

Response: The recovery Worker first reconciles the stable operation with external queue/accounting records. It attaches the existing Job if found. If not provably absent, keep the operation unknown and avoid a duplicate expensive submission. Record both the evidence and the remaining uncertainty.

This is a design exercise, not an incident report from a deployed service. Confirm actual behavior from task, process/job, artifact and policy records rather than from the final text alone.

Delivery checklist

  • Stable operation and distinct Attempt identities exist before side effects.
  • Crash points before/after submit and before/after artifact registration are tested.
  • Late messages are fenced.
  • Cancellation and unknown states preserve actual facts.
  • Recovery checks artifacts and costs before issuing new work.
