What problem this chapter solves

Separate control, scientific execution and evidence storage so the system can explain results, recover failures and assign responsibility. A single overall status is not enough.

Control and computation are separate responsibilities

The interface/API receives the task, authenticates access and exposes state. The controller assembles context, proposes bounded actions and records decisions. Adapters and Workers run scientific programs in controlled environments. A domain validator checks real objects and outputs; reporting cites the artifacts. Modules can share one repository. Separate processes when restart, resource or trust boundaries justify it, rather than creating a microservice for every box.

Represent a computation as related entities

Task and immutable TaskRevision capture the request. A preallocated Run captures one configuration and cumulative budget. A FrozenTaskSpec captures the scientific definition; PlanRevision and Step capture execution dependencies; Attempt captures actual execution; an optional external Job captures scheduler facts. Artifact records immutable bytes and parents; Validation records a versioned judgment. Feedback is evidence requiring reproduction. Distinguishing these identities lets one task have several reproducible Runs without counting internal retries as new experiments.

Distinguish state and storage types

Graph state is a working projection for the next decision. The business ledger owns execution, authorization, budgets and events. A checkpoint stores the graph position and state needed to resume. Files/object storage holds structures, trajectories, tables, logs and plots, while a retrieval index holds task-authorized knowledge references. An index hit does not replace original provenance; a checkpoint is not evidence that an external side effect executed exactly once.

Keep a reliable handoff between transactions and dispatch

Persist the operation identity, Attempt intent, budget reservation and outbox event within an explicit database transaction. A dispatcher claims work with a durable lease and passes the stable identity to the executor. Delivery may duplicate; the executor and ledger must recognize the same logical operation. Database, filesystem, model service and external scheduler do not share a magical common transaction.

Make lineage answer where a conclusion came from

A metric must point to the exact input bytes, scientific specification, mapping, code/environment version, producing Attempt and checker policy. Reports are derived artifacts, not mutable replacements for the original result. Keep failed and superseded candidates, while controlling their visibility and retention. Access checks apply to derived objects and cache hits as well as original input.

Failure scenario and response

Scenario: The UI says success, the Worker wrote a file and the database has no accepted Artifact record.

Response: Reconcile the dedicated output slot against the ledger, check hash and completeness, then register or quarantine it. Neither a file name nor a final chat message may create authoritative success.

This is a design exercise, not an incident report from a deployed service. Confirm actual behavior from task, process/job, artifact and policy records rather than from the final text alone.

Delivery checklist

  • Every fact has one owning component.
  • Run, Plan, Step, Attempt, Job, Artifact and Validation can be joined.
  • Graph state and durable execution facts have separate roles.
  • Crash points around dispatch and publication have a recovery path.
  • Report metrics preserve input and producer lineage.
