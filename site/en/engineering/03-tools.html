What problem this chapter solves

A maintainable capability includes its scientific meaning, execution environment, I/O, resource needs and checks. Being callable is only one part of being usable.

Maintain a capability contract

For each operation, define purpose, applicable data, preconditions, typed parameters/results, units, selection policy, version/license, resource class, error semantics and independent reference tasks. Distinguish registration, deployment health, reference passage and per-project authorization. Expose only the currently executable authorized set to the planner. A tool count is not a scientific coverage measure.

Use adapters to separate model and program interfaces

The model passes typed artifact references and scientific parameters. An adapter resolves authorized input, validates it and calls a fixed library function or argument-safe program entry point. It captures return code, logs, outputs, measurements and structured errors. It does not allow model-supplied host paths, shell fragments or package installation. Preserve original bytes; normalization and preprocessing must create documented derivatives.

Choose backends from the computation

Small checks and geometry can use restricted synchronous CPU execution. Long jobs should use an asynchronous Job protocol with status, heartbeat, cancellation and artifact collection. GPU predictions and HPC simulations need their own resource, environment, license and acceptance contracts. For P0, use the tested CPU path and clearly reject unsupported backends; do not manufacture a scheduler Job in a teaching fixture.

Make resource requirements visible to the plan

Declare CPU/GPU, memory, disk, wall time, model-call and output requirements. Queueing is a separate latency component from computation. Reserve resources atomically under a cumulative Run budget and enforce actual limits at execution. Unknown billing remains unknown. A larger request should queue or be rejected with a reason, not silently shrink its scientific object.

Rebuild environments and test upgrades

Pin code and dependency/image digests, model weights and database versions when applicable. A reproducible environment still needs reference tasks on real and negative inputs. Parser, numerical kernel, tool or validator upgrades require corresponding regression. Identify environmental assumptions rather than treating an example notebook that ran once as a reusable production method.

Keep four orchestration roles distinct

Agent orchestration chooses bounded next actions; a durable task service owns state and recovery; a scientific workflow defines domain dependencies; an HPC scheduler allocates and monitors compute resources. Existing validated domain workflows can be registered as composite tools. MCP provides a tool interface, not a job scheduler, a sandbox or scientific validation.

Failure scenario and response

Scenario: A registered tool is visible but its scientific environment is broken.

Response: Mark that version unavailable, preserve the execution failure and repair the environment through the maintainer process. Do not let the model invent a substitute command or claim that registration proves execution.

This is a design exercise, not an incident report from a deployed service. Confirm actual behavior from task, process/job, artifact and policy records rather than from the final text alone.

Delivery checklist

  • Every exposed capability has a tested adapter and scientific acceptance.
  • Parameters and host process arguments are separated.
  • Environment, license, version and resource assumptions are explicit.
  • Error classes distinguish input, policy, environment, transient and scientific failures.
  • An upgrade is checked against old and new reference inputs.
