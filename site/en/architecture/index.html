Architecture, framework, model and scientific tools

Architecture allocates responsibilities: who owns a fact, who may act, how failures recover and which evidence supports delivery. A framework offers reusable control/integration; a language model proposes interpretations/actions; scientific tools compute from actual data; infrastructure persists and restricts those operations. An architecture diagram is a design, not proof that its interfaces are implemented.

Use one LangGraph control graph and optional LangChain integration components. Keep actual work in tested scientific adapters and restricted Workers. Do not add a second multi-Agent framework before a controlled experiment demonstrates that role separation adds value under the same tools and budget.

Working state, checkpoints and authoritative facts

The graph state is the minimal permission-filtered view needed for the next decision: candidate/frozen spec references, object summaries, available tools, observations, pending questions and remaining budget. A checkpoint records where the graph should resume. The business ledger records what truly happened, who authorized it, what it cost and which artifacts were published. These roles may share a PostgreSQL instance but not ambiguous ownership.

Typed tasks, frozen science and versioned plans

Typed I/O lets code reject malformed shapes, but scientific semantics and authorization still require separate checks. Preallocate the ANALYZE Run before model work. Candidate specs evolve through appended events; freeze once before ordinary scientific TOOL execution. Formal plans bind frozen_spec_id. A same-contract repair appends a PlanRevision; a post-freeze change in the scientific question creates a linked new TaskRevision and Run.

Materialized mappings and pair-index artifacts can be computed later as long as they satisfy the frozen mapping/selection policy. Preserve the distinction between the scientific rule and the bytes produced when applying it. Ordinary TOOL Attempts need a compiled plan/spec/step; registered PREFLIGHT inspection and MODEL Attempts have their explicitly defined pre-freeze rules.

Extend through a complete capability package: purpose, preconditions, typed contract, adapter/environment/license, resources, error/retry semantics, validator, reference tasks and report rules. Registration, deployment health, reference acceptance and current authorization are separate states. Never infer trajectory, docking, map interpretation or HPC readiness from CPU geometry scores.

From a question to accepted evidence

  • API stores the original request and preallocates one ANALYZE Run, freezing identity/configuration/scope and reserving the total budget.
  • PREFLIGHT inspects actual input; the controller interprets intent and asks necessary questions within that Run.
  • The scientific contract freezes; the model proposes a plan and deterministic code compiles and authorizes it.
  • The dispatcher persists each Attempt/operation and resource reservation before a restricted Worker executes.
  • Artifacts are verified and published; independent scientific checks produce ACCEPTED, REJECTED or INCONCLUSIVE records.
  • Bounded same-contract revision uses real observations and the remaining budget. Reporting cites actual validated outputs and states limits.

Asynchronous execution, leases and reconciliation

Use durable intent, stable operation_id, request digest, lease owner/epoch and explicit Attempt state. Commit business transitions and outbox events together. A replayed graph node first consults the ledger. A lost acknowledgment is not proof that the job was never submitted. A stale Worker must fail fencing before publication.

A crash after writing bytes but before registration leaves an output slot to reconcile, not a valid public artifact. Close writes, verify size/hash, then publish immutable metadata. Cancel requests must be reconciled with actual process/job cleanup. UNKNOWN blocks dangerous resubmission and remains visible with unresolved cost. P0 does not claim a real Slurm recovery path.

Four different judgments

JudgmentEvidenceOwner
ExecutionActual adapter/process/Attempt outcome and collected filesExecutor and business ledger
Scientific acceptanceCorrect objects, mapping, units, invariants/references and applicabilityVersioned domain validator
Report reviewClaims and values trace to artifacts and stay within supported inferenceReport compiler and domain review
Experiment scoreFrozen external references, complete denominators and controlled comparisonEvaluation harness / scientific reviewer

The first three support runtime delivery; the fourth assesses the system. Shared validator/reference dependencies must be disclosed. Neither a confident explanation nor an exit code upgrades scientific_status.

Retrieval, context and reusable experience

Retrieve only currently authorized and task-relevant tool documentation, scientific methods and historical evidence. Supply the model with summaries plus stable artifact/document references. Keep full structures, trajectories and logs in controlled storage. Documents and tool observations may inform action selection but cannot grant new permission.

Preserve provenance, source versions and applicability when reusing prior plans or feedback. A stored reflection is a hypothesis about what helped, not new ground truth. Revalidate cache integrity and access and prevent hidden acceptance labels or scorers from entering retrieval/memory.

Minimal initial deployment

Deploy API, one controller, a restricted CPU Worker, PostgreSQL and immutable project storage. Keep model credentials in server connectors. Reserve the existing documentation port for the static resource site; its availability is not an execution service or authentication boundary. Define new service ports, storage paths and identity integration separately.

Add a broker, dedicated object store, more Workers or HPC/GPU adapters only after measured demand or a domain requirement justifies the new operational contract. Scientific adapters must retain their I/O, permission and acceptance semantics when transport or scheduling infrastructure changes.

Events, usage and recovery drills

Record every model/tool Attempt, Run phase/state transition, budget reservation/settlement, artifact publication and validation. A sampled trace or UI progress event cannot replace durable authoritative facts. Correlate versions and stable IDs; minimize sensitive content. Track stalled state progression, unknown execution/cost, queue delay, rejected artifacts and unintended side effects.

Exercise restarts, late messages, lost submit acknowledgments, partial writes, disk pressure, denied actions, cancellation and restore. Preserve in-flight versions during releases. A useful recovery drill establishes consistency of process/job state, ledger and artifacts, not merely a responsive page.

These are proposed responsibility directories rather than claims of existing implementation. Define node inputs/outputs and durable side effects before wiring the graph. Recovery may replay code; each node must describe how it recognizes already-recorded work.

Front-end/API state and event sequence

The UI first reads an authoritative Run snapshot, then replays durable events after its cursor and reconnects without submitting a new Run. All actions still use HTTP APIs with current authorization, idempotency or expected versions. SSE delivers observations of state; it does not execute work.

Show execution, phase, science, budget and unknown liabilities separately. Read FrozenTaskSpec through its artifact reference and fixed schema registry; do not embed a comparison-specific JSON shape as the universal future TaskSpec. Download uses artifact_id with current ACL and integrity checks. Feedback is scoped to the same Run and project and begins as NEEDS_REPRODUCTION.

M0–M5 delivery and acceptance

Follow the PRD milestone IDs: M0 contracts/environment; M1 deterministic scientific slice; M2 real model and workbench; M3 effective boundaries and pilot readiness; M4 frozen acceptance and bounded team pilot; M5 separately accepted P1 extensions. Estimate staffing and dates from actual scope and environment, not from a generic template.

Architecture mistakes to detect early

  • Treating the model answer as an execution record or numerical reference.
  • Using graph memory/checkpoints instead of a business ledger.
  • Allowing model-provided roles, host paths or budget estimates to grant authority.
  • Silently changing a scientific question during repair or resetting cost with a planning Run.
  • Retrying an unknown external side effect rather than reconciling it.
  • Using a tiny fixed demonstration to claim all-task structural-biology generality.
  • Adding many tools, frameworks or services before object identity and scientific acceptance work.
  • Calling a mock policy fixture an operating-system sandbox or production authorization system.
